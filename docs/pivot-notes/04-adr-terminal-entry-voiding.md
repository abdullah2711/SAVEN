# ADR: terminal soft deletion of posted entries

Status: Owner-authorized design; implementation and release evidence outstanding.
Date: 16 November 2026 (Asia/Karachi).
Authority: explicit Chartered Accountant owner override, decision D-013. This supersedes any requirement that a posted entry must remain active forever; it preserves physical source immutability, retained evidence and append-only audit. It does not authorize production migration or cutover.

## User behavior and retained representation

Users with the separately authorized delete action can delete posted entries. The command is a terminal void: the entry disappears from the active General Ledger and appears as VOIDED in a separate Deleted/Voided Entries filtered view. Choose views over moving or destroying source rows. Retain original journals, lines, accepted commands, evidence, numbering, corrections and operational history byte-for-byte. Add tenant_data.entry_voids, an append-only purpose-B record with a unique (tenant_id, entry_id) reference to the tenant-scoped source. A source historically posted remains historically posted; its effective lifecycle becomes VOIDED when this record exists. Every exposed lifecycle projection must honor that overlay. No generic journal status column is assumed.

Exactly one terminal transition POSTED -> VOIDED is possible. No runtime UPDATE, DELETE, TRUNCATE, unvoid, replacement tombstone or late attachment/effect mutation is permitted after voiding, including through parent cascades, helpers and retries. Existing posted sources remain protected by 040. A new entry requires a new identity/number and explicit historical linkage. Permanent voucher numbers and high-water marks are retained and never recycled.

Define tenant_data.active_general_ledger and tenant_data.voided_entries as canonical projections. Exclude all lines of a voided journal together, never selected lines. Active balances, trial balance, financial reports, exports, search and downstream consumers must use the same effective inclusion rule; hiding a register row alone is insufficient. Historical/as-of reconstruction must distinguish original posting and later void time while retaining both events. Do not both exclude an original and add an active opposite journal for the same void: that would double-adjust balances.

## Transaction and linked effects

The canonical void command locks the source and affected dependency set, rechecks tenant/company/branch authority, current policy, period controls and any required approval, then commits terminal record, reconciled effective effects, immutable command receipt, native-compatible audit, audit_event and outbox atomically. Use exact financial arithmetic. Store a server-verified actor (including canonical UUID mapping), source identity/version/digest, reason, original and effective state, event time, policy/approval version, correlation and idempotency binding; preserve original payload/evidence and effect references. Audit readers must be able to reconstruct the before/after inclusion and exact effect set.

A balanced journal cannot be removed from the active GL while leaving inconsistent AR/AP, payment allocations, tax schedules, stock valuation or other linked balances. Define the supported dependency graph and reconcile the entire affected bundle in one transaction. Existing posted correction/reversal pairs must remain linked; do not void just one side and leave an unintended net balance. Physical stock movement or customer custody is not undone merely by an accounting void. Unsupported dependency cases must return an explicit refusal without partial effects and remain release limitations until a reviewed operational workflow exists. This is not permission to prohibit deletion of all posted entries: the initial supported plain-journal path must succeed. Closed-period handling remains policy-controlled and attributable, never a silent historical rewrite.

Original POSTED receipts remain immutable; a distinct void command has its own durable VOIDED receipt. Same actor/key/digest retries return the original result without another mutation/event; key reuse with different input fails. Concurrent voids yield exactly one terminal event; a later distinct delete cannot delete again. Failed/denied attempts require independent durable security audit, not an INSERT that disappears with rollback. No generic trigger coverage may be used to claim unaudited voids are safe pending PIVOT-006.

## Visibility and authority

Only Senior Accountants, Management and Auditors may see the Deleted/Voided Entries page or retained voided contents. Juniors cannot. Enforce this on the server and at the database read boundary, including direct source/line/evidence reads, audit drilldowns, old URLs, search, exports and AI tools; a filtered view or hidden menu alone is insufficient. Tenant/company/branch scope still applies. Preserve retained source audit without exposing voided financial contents through its before/after payloads to juniors.

Separate accounting.entry.void from accounting.voided_entries.read. Read eligibility does not grant deletion: auditors are not writers by virtue of visibility. Conversely, the owner restricted visibility, not all deletion to these three groups; an independently authorized user can void and receive a minimal receipt without permission to browse retained contents. Protected server-managed eligibility maps Senior Accountant/Management/Auditor responsibilities to the read capability. Arbitrary custom role names, a client flag/header or self-assigned permission cannot grant it; protect eligibility assignment under existing owner/management administration rules without redefining the immutable ultimate-owner role.

All new tenant tables have composite tenant keys, ENABLE plus FORCE RLS and atomic grants with policy installation. saven_customer_app remains the sole direct tenant grantee. Additive restrictive read guards on existing source/evidence/audit tables, or revoked direct read paths with constrained interfaces, must close raw-table bypasses without permissive-policy widening. Reads use verified principal context and server-resolved protected eligibility; RLS is not a replacement for configurable business action/approval rules. No runtime superuser/BYPASSRLS, admission-owner privilege expansion or broad definer owner. Do not reuse saven_tenant_admission_definer for financial access. If a constrained definer is necessary, document and prove its minimal non-login authority, fixed search_path and restricted execution. Private must implement these controls locally without vendor authority.

## Existing flows and migration ownership

Native correction creates a linked opposite journal and retains its original. Native rejection/return concerns pending decisions/revisions, not a posted deletion. Preserve these baseline flows; neither is an alias for void. Pending edits still create attributable revisions and invalidate approvals. A void is a separately authorized terminal operation with its own audit and dependency semantics.

PIVOT-005 retains immutable payload 040 and adds 042-entry-voiding.sql for schema, protection, effective read boundaries and atomic void database primitive; no applied 040 bytes are edited. Preserve worker-b's current uncommitted 040 work for review, not as accepted evidence. At revision time no committed/applied 040 delivery has been verified by this engineering note. Dispatcher registration is explicit: 040 then 042 now; after PIVOT-006, 040 then 041 then 042 on clean installs, with version-aware upgrade registration that never reapplies an installed payload. Loading only the numerically newest payload is forbidden: both original protection and new audit/void protections must remain attached. Ensure an upgrade installs all new policies/grants before exposing reads or the primitive.

PIVOT-005 must protect its void receipts/audit records now, without editing the future 041 payload. PIVOT-006 subsequently owns generic audit coverage and must preserve single logical-event identity, retained native audit and nonrecursive behavior. AUTH-006 gates acceptance of real application identity/capability integration; fixture context is test evidence only. PIVOT-013 owns application command/policy/adapter integration and all active query consumers, before PIVOT-009 tests the extension lane. PIVOT-005 does not wire a production route or build a page. A future UI contract must provide a real Delete confirmation/reason flow and the restricted Deleted/Voided Entries page before this behavior can be called delivered.

## Required evidence and extension points

PIVOT-005 tests must prove: successful plain-journal void with exact balanced active totals and retained raw bytes/numbers; terminal no-update/no-delete/no-unvoid/no-new-children protection; rollback on audit/outbox/effect failure; idempotent replay and concurrent duplicate/void-versus-post races; cross-tenant denial; Senior Accountant, Management and Auditor visibility versus junior denial across views and raw source/evidence/audit paths under actual runtime roles; client-role/capability spoof denial and permissive-policy widening resistance; explicit linked dependency refusal/reconciliation; fresh install and upgrade preserving 040 checksums and attachments. Report which tests actually ran and remaining AUTH-006/kernel/UI limits. Do not substitute mocked rows or privileged migrator reads for customer-role proofs.

Reference domains/action registrations remain extensible, effective-dated and schema-versioned; add VOIDED and void/read actions through the canonical reference annotation/JSON seed mechanism rather than growing CHECK lists or custom-name authority. Executable handlers remain registered and reviewed. Dependency reconciliation is behind module interfaces, not concrete cross-module imports. This narrows terminal void to irreversible retention by owner direction; a future owner-approved ADR and additive migration would be needed to change that rule, never rewriting prior events. SQLite/reference code, source data, tests and applied migrations stay preserved. Baseline parity is unchanged; new void semantics have independent expected results in an explicit extension lane, not weakened assertions or a claim of existing SQLite support.
