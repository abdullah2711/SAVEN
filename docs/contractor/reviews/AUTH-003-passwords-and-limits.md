Findings requiring correction:

1. **HIGH — verification bypasses the KDF concurrency/input bound.** `src/auth/password-policy.mjs:182–194`: invalid/oversize input calls `dummy(password)` before admission, and the saturated `bounded` fallback also calls `dummy(password)`. Each starts another native Argon2 job outside the counter. A burst over distinct accounts therefore exceeds `maxConcurrentKdfs` rather than being refused; the hash-only concurrency test misses this. Oversize input is also copied into a KDF buffer rather than replaced with bounded dummy input. Apply admission to every derivation, including dummy and compatibility paths, and refuse overload without starting more KDF work. Validate finite absolute verification caps and encoded salt/tag lengths before native allocation; currently `maxMemoryKiB/maxPasses/maxParallelism` can themselves be raised without an absolute validation bound, and decoded tag/salt lengths are unchecked. Return a consistent bounded verification result or controlled busy error. Require instrumented concurrent verify/dummy/mixed-scheme tests across accounts, oversized inputs, hostile stored parameters and recovery after overload; do not rely only on timing or concurrent hash calls.

2. **HIGH — dummy verification exposes a distinguishable account/verifier path.** `password-policy.mjs:127–136` uses one Argon2 pass, while ordinary new verifiers use three. `verifyArgon2id:161–166` returns immediately for out-of-bounds parameters; malformed salt/tag or native-provider failures can instead throw. An unknown identity, ordinary wrong password and malformed stored verifier thus do not follow the claimed equivalent bounded failure path (and some produce 503 rather than generic credential failure). Use a reviewed dummy-verification strategy matching the configured normal workload, document compatibility-scheme timing limits honestly, and normalize invalid verifier shapes without an immediate/no-work account-dependent branch. Add deterministic provider/work-parameter assertions for absent, unknown, malformed and valid-but-wrong credentials; identical JSON assertions alone do not establish the invariant. Native parameter constraints must follow the pinned Node 24 API, not only the regex.

3. **HIGH — provider/error paths escape durable attempt accounting; ingress can trigger this.** `routes.mjs:204–217` awaits verification/rehash without an exceptional-attempt outcome. A throw escapes `rate-limit.mjs:150–154`, rolls back and returns 503 with no failure row, leaving the budget unchanged. Moreover, the retained `createAuditWriter` unconditionally reads request `cf-connecting-ip` into an `inet` column, even when the new limiter's trusted header is disabled. A client-supplied invalid value can fail the failure audit after KDF work and roll back its accounting; a valid value contradicts the report's blanket claim that no raw ingress value is stored. Validate/sanitize ingress at the trusted boundary and ensure default-off request headers cannot influence audit persistence. Persist a sanitized exceptional-attempt/security outcome through a deliberate durable path, while preserving atomic successful rehash/session/audit and withholding cookies on failure. If the audit store itself is unavailable, fail closed and state the evidence limit rather than claiming guaranteed durable logging. Add injected verifier/rehash/session/audit errors and malformed/spoofed-header tests asserting bounded work, no session/cookie on failure and the next request's budget. An infrastructure-wide inability to write must not silently become unlimited KDF admission.

4. **HIGH — limiter event order is not the serialized attempt order.** `rate-limit.mjs:106–113` discards failures whose `occurred_at` is not greater than the latest success. The audit writer omits this field, whose schema default is PostgreSQL `now()` (transaction-start time). Attempts begin their transactions before waiting for advisory locks. A failure transaction that starts before a success transaction but acquires the scope lock after that success can record an older timestamp and be excluded from the count. Equal timestamps also lose ordering. Application-injected check time and database-default event time are separate clocks, so the current clock-advance test does not prove durable reset/window boundaries. Establish one authoritative post-lock time/order for throttle events, with an unambiguous tie strategy, without rewriting append-only history. Test an intentionally delayed pre-success transaction acquiring the lock after success, equal-time failures, window expiry and concurrent reset/login histories. PostgreSQL documents that `now()` is fixed at transaction start, unlike actual wall-clock time: [date/time functions](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT).

5. **MEDIUM — restricted-role and composition evidence is missing for the new paths.** `tests/auth-003-passwords.test.mjs:18–27` builds operation pools from the provisioning PGUSER (default `postgres`); the focused cases do not create/use a restricted auth-service login. They manually compose routes instead of exercising the retained `createAuthServer` entry point. Prove the new conditional rehash UPDATE, advisory locks, audit reads/inserts, successful session and failures through a real non-owner/non-superuser/non-BYPASSRLS auth-service login, with forbidden financial/DDL access still denied. Include the real composition path, not only direct factory injection. Record role identity and exact evidence boundaries. Do not expand grants or use a privileged pool to make this pass.
