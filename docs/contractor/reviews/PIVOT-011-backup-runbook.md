## Required corrections

1. **P1 — PITR is not actually activated and the restore is insufficiently isolated (§6).** Recovery settings alone do not enable targeted archive recovery: the procedure omits creation of `recovery.signal`. Its restore_command comment says “to stdout”, whereas the restorer must put the validated decrypted segment at `%p`. Add the signal and correct the destination/exit-status contract. Require new isolated storage for PGDATA, WAL and every tablespace; checking only that PGDATA differs from the source does not prevent restored symlinks or WAL tablespace-creation records from targeting source paths. Explicitly fence restored credentials/connections, source replication and inherited archive publication before startup; a different loopback port is not an authorization fence. Promotion for this drill must never enable business writes or write to the source archive. PostgreSQL documents the signal/destination requirements in [recovery configuration](https://www.postgresql.org/docs/18/runtime-config-wal.html#RUNTIME-CONFIG-WAL-ARCHIVE-RECOVERY) and the source-path risk in [PITR caveats](https://www.postgresql.org/docs/18/continuous-archiving.html#CONTINUOUS-ARCHIVING-CAVEATS).

2. **P2 — the selected backup format and verification command disagree (§5).** `--format=tar --gzip` is followed by bare `pg_verifybackup "$target"`. PostgreSQL 18 permits tar verification, but requires `--no-parse-wal` there; WAL parsing is supported only for plain format. Prefer plain format with streamed WAL and `--manifest-checksums=SHA256`, followed by full pg_verifybackup, then encrypt/package for off-host retention. Document tablespace/WAL path handling and verify the retrieved/decrypted copy before recovery configuration or startup modifies it. If tar is retained, explicitly separate its limited verification from extracted plain-format WAL verification. See [pg_verifybackup](https://www.postgresql.org/docs/18/app-pgverifybackup.html) and [manifest options](https://www.postgresql.org/docs/18/app-pgbasebackup.html#APP-PGBASEBACKUP-OPTIONS). Neither choice substitutes for a drill. Also remove `data_checksums = on` from postgresql.conf: it is not a settable configuration parameter. Specify initdb policy, SHOW observation and any separately authorized offline pg_checksums procedure; checksums can be changed on a cleanly stopped cluster, contrary to the current “cannot be changed later” statement. See [pg_checksums](https://www.postgresql.org/docs/18/app-pgchecksums.html).

3. **P1 — the archive wrapper does not meet its own publication/idempotency contract (§4).** It PUTs directly to the final off-host name; the only temp-to-final rename is local and after upload. Existing remote content can be overwritten before comparison, and randomized encryption makes a repeated ciphertext digest differ even for the same WAL. Replace the shell skeleton with a precise placeholder interface: cluster/system-id plus timeline-qualified namespace, remote staging, durable verify-before-publish, atomic no-replace publication, verified same-source-content retry success, mismatch refusal and nonzero exit on failure. Do not invent provider code under this contract. Existing archived bytes must remain immutable; [PostgreSQL archiving guidance](https://www.postgresql.org/docs/18/continuous-archiving.html#BACKUP-ARCHIVING-WAL) requires content comparison and durable success for retries.

4. **P1 — baseline and recovery boundary can describe different committed states (§6 Steps 0–1).** Step 0 captures separate queries while writers can still run; fencing and the chosen LSN occur later. A correct restore can therefore differ from that baseline, or inconsistent snapshots can obscure missing work. Fence and drain all named test writers/jobs first; capture a consistent snapshot and transaction-aligned target under that fence. Record the source system identifier, target timeline, base manifest/WAL range and exact recovery target; select/verify the segment containing that target, not merely the most recently archived segment after a switch. Make source SQL/OS responsibilities explicit: the read-only reconciliation role is not automatically entitled to control/checkpoint functions, and the replication connection needs an actual separately provisioned LOGIN principal. Keep the fence through baseline/target capture and distinguish pre-drill observations from the authoritative comparison snapshot.

5. **P1 — the proposed success checks can falsely pass (§§7,10).** The owner queries group only existing owner rows, so zero-role/zero-owner tenants disappear; they also omit active-principal/admission checks. Anchor them to the expected activated-business set and check exact active ownership. The audit hash excludes actor/detail/command bytes and does not hash audit_event contents; use deterministic complete-row canonical digests and counts for both independent streams without historical backfill. Counts alone do not prove command/review/idempotency payload preservation. Cover missing parent/child and stock rows in both directions, and either supply linked allocation/credit/GL controls plus object/evidence-manifest checks or label the unsupported portions as blocking unimplemented checks rather than implying §10 proves them. The RLS snippet supplies no verified user or real runtime role and can return zero because all access is denied or the fixture is empty; require known own-tenant rows, verified user/tenant context, own-access positive control and denied foreign access under the actual non-owner role after PIVOT-004. Mark truly unavailable pre-RLS checks not applicable, never passed.
