## Required corrections

1. **P2 — PKCE ciphertext can lose its key binding.** `db/postgres/05-auth-schema.sql:460` checks `code_verifier_ciphertext IS NULL OR code_verifier_key_version > 0`, while the key-version column is nullable. A row with otherwise valid state/expiry, a 16-character ciphertext and NULL key version satisfies that CHECK as UNKNOWN. It therefore admits an encrypted verifier with no key-version binding. Add a null-safe constraint requiring a non-null positive key version whenever ciphertext exists, and actual INSERT/UPDATE regression cases for null, zero and negative versions, plus valid optional/valid-encrypted rows. This follows the account-token/TOTP versioned-encryption convention already present. PostgreSQL CHECK accepts TRUE or NULL, as documented in [PostgreSQL constraints](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS). This is a schema-readiness defect, not a claim of an exploitable live OAuth route.

2. **P2 — audit rollback evidence can be false green.** `tests/auth-001-schema.test.mjs:618–629` nests BEGIN/ROLLBACK inside the fixture's transaction and ends the entire action with `.catch(() => {})`. If either INSERT fails, the later zero-count assertions still pass. Remove blanket suppression; prove both rows existed inside the transaction, trigger an explicit expected rollback through the fixture's transaction owner, and assert that only the intended failure was observed before checking persisted counts. Keep the independent committed failure-event check. Cleanup failures in the bootstrap test at lines 812–815 must also be surfaced/aggregated rather than silently leaving cluster objects while reporting success.

3. **Evidence correction — supported runtime and reviewed pins.** The delivery explicitly records Node `22.23.5`; the project requires `>=24.13 <25`. Provide revised gate output with `node --version` under that supported range, exact revision and dedicated-cluster configuration. The displayed environment-prefix command applies its variables only to the first command before `&&`; show an exported environment or an invocation that supplies the opt-in to the actual test process. Preserve earlier results as historical evidence. Pinning `better-auth` and `@better-auth/passkey` exactly is appropriate, but successful dependency resolution alone is not the ADR's licence/runtime/advisory/schema-adapter review. Record dated official sources and the pinned-version findings, including any required custom adapter work. Do not enable plugins or change pins merely to satisfy this documentation request; an actual pin change needs a scoped follow-up.
