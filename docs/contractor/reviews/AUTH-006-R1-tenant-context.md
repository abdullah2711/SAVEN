Required correction (remaining part of dc183a2 finding 1):

1. **HIGH — complete membership/role admission serialization and bind the exact current role.** `readMemberships` uses an unlocked joined SELECT. `withAuthority` builds `resolved.roleId` from its initial read; final `assertAdmission` compares membership id, tenant, epoch and usability but does not compare `selectedNow.role_id` with the resolved role. Thus a committed role change with no epoch bump between those reads can pass when the new role does not require MFA, leaving a stale role in the supposedly verified context. The new test already demonstrates that role changes without epoch bumps are possible, but covers only promotion to an MFA-requiring role. Changes after the final read can also commit while the handler uses the earlier authority. The report correctly requests an additive interface and explicitly says this residual window remains; this is incomplete correction, not an authorized relaxation of the gate.

   Complete a narrow locking/validation protocol for the canonical membership and assurance-role authority used by admission, held through the business transaction with a deterministic lifecycle-compatible order. Include the full authority set that can make MFA mandatory, and account for new membership/role associations rather than claiming row locks alone prevent insertion. Resolve and bind the exact current selected role (or fail closed when the stored selection is stale); verify the final context cannot retain an earlier role after a committed change. Preserve least privilege, forced isolation, existing admission-owner authority and one business client. Do not add permissive membership UPDATE authority to the auth-service runtime merely to permit a locking SELECT.

   The report's requested migration/interface is outside current TOUCH and is **not authorized by this review**. Before implementation, supply a concrete bounded amendment proposal naming the additive path, function API, dedicated owner/column privileges, RLS behavior, caller/context validation and affected fixture/tests; the engineer can issue the corresponding contract amendment. No need to rerun the unchanged gate to restate this known dependency. Once authorized, prove both orderings with real restricted roles: invalidation wins before admission (no handler/effects), or admission wins and the conflicting change blocks until completion. Cover selected role changes without epoch bumps, role policy/effectiveness changes and membership addition/promotion affecting MFA, as well as revocation/epoch changes. Include smallest supported separate auth/business pool composition. Preserve honest uncertainty handling if the auth transaction fails after the business commit; the two transactions are not a distributed atomic commit.
