Required corrections:

1. **CRITICAL — a single authentication method is promoted to MFA, and policy can select assertion-only assurance.** `defaultAssurance` treats any one of `otp`, `hwk` or `swk` as access_mfa. Those methods are not independently proof of multiple factors; the AMR registry distinguishes them from the explicit MFA indication. A correctly signed assertion with only `amr:['otp']`, an active access_mfa mapping and the default policy therefore passes. Also, requiredAssurance accepts any nonempty string: configuring it and the mapping as access_asserted admits an assertion with no MFA evidence. An equality of labels must not disable the mandatory operator-MFA invariant. [RFC 8176 section 2](https://www.rfc-editor.org/rfc/rfc8176.html#section-2) defines the method semantics; the bypass conclusion is from this source, not a live-provider test.

   Require explicit, positively verified MFA evidence under a documented trusted Access/IdP policy. Individual methods may contribute only through a reviewed policy that proves the needed assurance, not this automatic inference. Keep the acting subject, assertion validation and assurance evidence distinct; configuration must not select assertion-only access as equivalent to MFA. A custom signed claim needs a documented issuer-controlled claim policy, not merely a nonempty string. Add signed-token negatives for each single method, absent/malformed/contradictory assurance and weaker configuration, plus valid supported MFA positives. Preserve reference/config extensibility without a hardcoded business-role shortcut or live Access policy change.

2. **HIGH — reserve current mapping authority at exchange and bind/revalidate it for subsequent operator use.** Exchange reads mapping/user/role without locking or the accepted authority protocol, samples time before pool checkout, then creates a session. A mapping can be revoked/reassigned or role/assurance changed after that read and still produce a usable credential. More directly, exchange once, revoke access_identity (or expire/deactivate its operator role), then call operator/me: it only reads/refreshes auth.sessions. It has no subject/issuer/audience/mapping binding to revalidate and continues reporting the old operator role. Session rows contain only the local user/role, so multiple subjects for the same user cannot be distinguished. Source assertion expiry is stored in the nonce ledger but is not bound to session admission; the default local session can live far beyond it. Initial revoked-mapping tests do not cover this lifecycle.

   Provide an authoritative reusable operator-session resolution/admission protocol. Persist the exact verified issuer/subject/audience, mapping identity/version or equivalent binding, role, assurance evidence and reviewed validity ceiling associated with the issued session. Serialize conflicting mapping/principal/role changes against exchange and privileged admission, following the accepted gate-first/lifecycle order; do not claim a plain SELECT in a transaction reserves authority. Cover new mapping associations as needed and keep one owned client for each transaction without nested exhausted-pool checkout. Every current operator identity path, including generic operator-realm me where supported, must use current authority; define the interface future PIVOT-007 reads must consume. Revalidate revocation, reassignment, role/effective/assurance changes and expiry; do not rely on an unwired upstream proxy to supply this guarantee. Preserve logout cleanup and avoid routing operator sessions through the customer tenant boundary.

   Add controlled invalidation-first and exchange/admission-first interleavings, same-user/different-subject isolation, post-issuance revocation/role/assurance/expiry tests, smallest-pool composition and audit/nonce/session atomic failure cases. Keep application vs source-assertion lifetime explicit: no silent long-lived elevation beyond reviewed authority. Existing new SQL/module paths can carry the binding/protocol; any necessary edit outside TOUCH needs a bounded engineer amendment first. Do not edit applied 033 or add permissive runtime mapping UPDATE authority to obtain locks.

3. **HIGH — fallback replay identity depends on noncanonical bearer text.** Without identity_nonce, normalizeNonce hashes the raw JWT string. decodePart checks alphabet then uses a permissive base64url decode without canonical re-encoding. For a 2048-bit RSA signature, changing unused bits in the final base64url signature character can preserve the decoded signature bytes and the signed header/payload while changing that raw-string hash. A consumed assertion can therefore produce another ledger key and session through the fallback. Existing replay tests always generate identity_nonce and test the identical string. [RFC 4648 section 3.5](https://datatracker.ietf.org/doc/html/rfc4648#section-3.5) explains the multiple-encoding issue; this is a source-derived counterexample, not a reviewer-executed exploit.

   Require canonical JOSE encoding and/or derive the fallback identity from a stable verified assertion representation, with issuer/audience/subject binding as appropriate. Do not conflate unrelated identities' nonce namespaces. Add no-nonce replay tests using equivalent signature encodings, simultaneous exchanges and audit failure/rollback, asserting at most one committed exchange/session. Retain ordinary bearer validation reuse and the honest captured-bearer first-presenter limit; no impossible general replay-proof claim is requested.

4. **HIGH — freshness policy is not enforced at the owned admission boundary.** validate runs before acquiring the auth transaction; exchange's timestamp is also taken before checkout. A token valid at validation can expire while the pool is blocked and still issue a fresh session. Additionally maxTokenAgeSeconds silently does nothing if iat is missing, rather than refusing an assertion whose age cannot be established. Enforce source expiry, effective mapping/role windows and configured assurance/age freshness with the trusted current clock at final owned admission. Require a finite usable iat when a maximum-age policy is configured; validate numeric time inputs consistently. Add missing/invalid iat and a paused-checkout expiry/age test with no credential/nonce/success event committed. A long local session must not manufacture fresh upstream assurance.

5. **MEDIUM — key refresh cooldown is not safe under concurrency or failure.** lastRefreshAt advances only after the awaited refresh succeeds. Concurrent unknown-kid validations can all see the old value and invoke the callback, and a failing callback leaves it unchanged for the next request. This defeats the documented once-per-cooldown behavior and lets untrusted kid values repeatedly drive the fixed source. Reserve refresh admission before awaiting, coalesce/bound in-flight refreshes, and retain a retry cooldown on failure without losing known-good keys. Fail closed with sanitized errors and no token/URL-directed fetch. Add simultaneous unknown-kid, slow/rejected refresh, recovery and valid cached-key cases; the current rollover test is sequential and successful only.
