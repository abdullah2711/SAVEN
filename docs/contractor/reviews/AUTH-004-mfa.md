Required corrections:

1. **CRITICAL — password-only enrollment replaces an existing verified factor.** `routes.mjs` mfaEnrollRoute accepts only an empty body and requires session/CSRF/origin, then calls `factors.mjs:199–225` beginEnrollment. Its unconditional UPSERT replaces the existing seed, clears verified_at/replay/failure state and invalidates recovery codes without password reauthentication or proof of the old factor. Someone with the account password can obtain a pending session, call enroll, learn the new seed and complete enrollment, bypassing the actual enrolled second factor. Permit initial enrollment only when no verified factor exists; changing/restarting a verified factor must require explicit recent reauthentication plus the existing factor/recovery proof in a race-safe transition. Do not use an mfa_verified flag alone as proof of recent sensitive-action reauthentication. Add a fresh password-only session regression against an already enrolled account: seed/recovery state must remain unchanged and the request must fail; authorized replacement must still work. Audit enrollment/replacement as attributable lifecycle events without seed/code contents.

2. **CRITICAL — enforced membership RLS can silently remove the MFA requirement.** `factors.mjs:152–165` authority queries auth.tenant_membership with a user-id parameter but never binds verified transaction-local app.current_user_id. Accepted PIVOT-004/032 policies restrict auth-service preselection to that context; the parameter does not establish it. Login calls authority/status on the leased connection after reservation COMMIT, and status calls elsewhere use fresh clients. With the integrated RLS schema and restricted auth-service role, no-context membership reads return no rows and required becomes false, even for an administrator. Tests use provisioning PGUSER/default postgres and the auth-only fixture, hiding this condition. Resolve current authority through a constrained, server-verified principal boundary on the same transaction/client; no client ID, session-level SET, broad grant, superuser or RLS bypass. Distinguish unavailable/unresolved authority from a verified nonrequired user. Add actual non-owner/non-BYPASSRLS auth-service login tests with the accepted forced membership policies installed, including admin/ultimate owner, ordinary member, missing/malformed/stale context, promotion/revocation and reused pooled connections. Do not weaken PIVOT-004 to make this work. PostgreSQL explains policy filtering and privileged bypass: [row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html).

3. **HIGH — factor lifecycle changes do not invalidate assurance across sessions and race verification.** Disable downgrades only the current session; beginEnrollment downgrades none. Other mfa_verified sessions remain accepted even when no verified factor remains because pending checks trust the stored assurance label. Factor reads have no user/factor-level lock; locking one session does not serialize another session for the same user. A verifier can read an old seed, race disable/re-enrollment, then consumeStep using only row id/last_used_step and upgrade assurance after the factor changed. Enrollment completion has an analogous stale-seed race. Bind assurance to the current factor lifecycle and serialize user/factor transitions with deterministic lock order; invalidate/downgrade/revoke affected sessions on disable/replacement, without stale-verification resurrection. Preserve current credential/session guards and atomic factor/recovery/assurance/audit effects. Add two-session controlled races and committed-state checks: old TOTP/recovery cannot upgrade after reset, old verified sessions cannot bypass required assurance, and new valid enrollment remains usable. Keep any new persistent schema need outside TOUCH pending a narrowly revised contract; existing session invalidation mechanisms may provide a compatible solution.

4. **HIGH — retries are bypassable on enrollment/recovery and under concurrent sessions.** completeEnrollment increments failures but never checks locked_until; verifyRecovery neither checks the lock nor counts failures. beginEnrollment resets counters on every request. registerFailure reads an unlocked row then writes an absolute count, so parallel failures from different sessions can overwrite increments. Disable password verification also bypasses the durable password-attempt limiter. Apply bounded, durable admission/failure policy to every relevant endpoint and recovery path, including pending enrollment/restart and password reauthentication; preserve legitimate recovery semantics through an explicitly bounded policy rather than unlimited guesses. Serialize/atomically increment counters and preserve failures when the outward request is refused. Add cross-session bursts, locked enrollment attempts, recovery failures, repeated restart, disable-password failures and cooldown recovery; assert bounded verification starts and exact durable counts. Retain one-success-only recovery consumption. No new numeric production limits are approved by this review.

5. **HIGH — disable recreates nested pool checkout while holding a transaction/session lock.** `routes.mjs:614–616` enters store.withTransaction then calls findUserByEmail, whose retained composition implementation uses pool.query. On max=1 it waits for a connection held by itself; simultaneous disables can exhaust larger pools. Reuse the already owned transaction for reauthentication lookup and all factor work; preserve no-cookie-on-error and the accepted destroy-on-uncertainty helpers. Add a bounded-time restricted-role size-one disable success and saturated small-pool cases. Do not solve this merely by increasing pool size or using a privileged connection.

6. **MEDIUM — exposed cryptographic configuration lacks entropy/size and recovery-version validation.** validateMfaConfig bounds digits/period/window/count but not secretBytes or recoveryCodeBytes. `secretBytes: 0` is accepted with keys configured and creates the same empty TOTP seed for every enrollment; short seeds likewise contradict the claimed 20-byte random-secret invariant. Bound secret/recovery entropy and allocation before generating bytes, reject invalid/duplicate key versions, and make recovery hash-key version handling truthful: issueRecoveryCodes currently always stores hash_key_version=1 while recoveryDigest uses one unversioned injected key. Define rotation/retirement behavior explicitly rather than implying old recovery keys remain usable. Add malformed/weak/oversized configuration tests and retained encryption-key-version positives. No secrets belong in logs or fixtures beyond synthetic test material. Use independent [RFC 6238 test vectors](https://www.rfc-editor.org/rfc/rfc6238#appendix-B) for algorithm validation in addition to generating test codes with the implementation under test.
