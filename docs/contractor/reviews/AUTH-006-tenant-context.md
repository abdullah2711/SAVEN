Required corrections:

1. **HIGH — auth resolution and business admission do not share an authoritative transaction boundary.** `selection.resolve()` locks the session in `store.withTransaction`, returns its selection, and commits before `withTenantContext()` even checks out the business client. `tenant_data.session_admitted(tenant,user)` checks an active canonical membership, tenant principal and identity; despite its name it never reads `auth.sessions`, selected membership/epoch, credential generation or role effectiveness. Pause after resolution, revoke/rotate that session (or reset credentials while keeping the user active), then resume: the business admission predicate still returns true and the handler can write. Expiry during checkout has the same gap. Membership epoch/role changes, clearing or switching selection also leave the returned context stale. The report discloses only the epoch window, understating the session/credential window. Even the resolution transaction locks only the session, not all membership/principal authority it reads.

   Establish a defined linearization point that validates the exact session, customer realm, current credential generation, selected membership identity/tenant/epoch and active effective authority before business work, with a locking/provenance protocol that serializes conflicting changes. Keep one owned client for all business statements, least privilege, no nested checkout on the same exhausted pool and safe PgBouncer behavior. Do not broaden the existing boolean helper's grants or accept client ids as authority to work around this. If an additive database interface is required, request a narrowly specified contract amendment before editing outside TOUCH; this review does not authorize migration/grant changes. Add controlled pause/interleaving tests after resolution and before business admission for committed logout/revocation, rotation/reset, expiry, membership/role/epoch changes and cleared/switched selection. Assert the handler is not invoked and no business effects commit when invalidation wins; document the permitted ordering when business admission wins. Test the actual composed resolver/boundary with real restricted roles and smallest supported pool sizes, not only a stub resolver.

2. **CRITICAL — the reusable business boundary does not enforce required MFA or realm authority.** `readSessionById()` validates liveness but does not require customer realm or current MFA assurance; `selection.resolve()` only checks active membership and its epoch. No factor/assurance check occurs in `createTenantContext`. The auth HTTP pre-MFA guard protects the three selection routes, not future business handlers using this exported gate. For example, a member selects a tenant, then acquires a role requiring MFA while the membership remains active (or its factor lifecycle downgrades the session). Resolution can still return that selection and execute business work with a single-factor session. Direct use of the selector/resolver also lacks the routes' operator-realm refusal. This breaks ADR03's enrollment-only administrator access and the accepted AUTH-004 assurance requirement.

   Make verified realm and current required assurance part of authoritative business admission, under the same lifecycle/transaction protocol as correction 1. Resolve requirements from active/effective assurance-role data, revalidate current factor enrollment and lifecycle-bound session assurance, and fail closed on unresolved requirements. Preserve the injected module boundary; do not introduce hardcoded business role names or make each caller remember an optional guard. Apply appropriate checks inside tenant selection as well, so a route-level read-before-mutation guard is not the sole defense. Add real composition tests for pending/enrollment-only admin sessions, member-to-admin promotion, factor disable/replacement or assurance downgrade after selection, unresolved authority, operator-realm refusal, and a valid verified-admin positive. Include changes paused between the route precheck/resolution and final admission. Existing eight tests seed ordinary `member` sessions and cannot establish this invariant.

3. **MEDIUM — company/resource evidence and guidance do not satisfy the contract.** The report labels T2 company/account invisibility from T1 context as company/resource denial; that proves cross-tenant isolation only. It never demonstrates a forbidden company/resource inside the selected tenant while allowing an authorized one. The DB README also recommends putting company/branch/resource restrictions in additional RLS policies and policy tables, conflicting with CONVENTIONS' prohibition on configurable per-tenant business rules in RLS. Correct the guidance: forced tenant isolation complements the shared business authorization layer; it does not replace it. Add a meaningful same-tenant allowed/denied company/resource composition test through this boundary using the relevant authorization interface, and show the denied write leaves no effects. Do not claim this generic wrapper implements the full future business policy engine or expand into out-of-scope accounting implementation. If the required interface is unavailable, identify that acceptance dependency explicitly rather than relabeling a cross-tenant test.

What is sound in this delivery: selector JSON accepts exactly one tenant/membership request and resolves it against the stored session principal's memberships; header/query selectors are ignored and unknown body user fields refused. Context settings are parameterized with transaction-local `true`, verified on the business client, and passed with frozen server-resolved metadata. The boundary itself does not call `pool.query`. Ordinary handler failure rolls back; uncertain BEGIN/COMMIT and failed rollback paths mark the business client for destruction.
