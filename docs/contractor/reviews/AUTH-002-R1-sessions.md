## Required corrections

1. **P1 — the actual library path accepts disabled/stale identities.** In `server.mjs`, createBetterAuthSessions.findOne(session) checks session expiry/revocation, but neither that path nor its user join validates auth.users.status or equality of the session and current credential_version. Its libraryUser projection omits those security fields. Thus the tested `context.internalAdapter.findSession(token)` can still return a session/user after disabling the identity or incrementing its credential epoch. The first-party store correctly rejects these conditions; the library adapter must enforce the same rule. Add real-library negative tests for disablement, epoch changes, revocation, wrong realm and expiry, including affected lookup/list/count paths. An isolated composition path is still executable delivered code, not an exemption from session authority.

2. **P1 — library updates can resurrect idle-expired sessions and exceed idle policy.** Adapter update/updateMany match only revoked_at IS NULL, then replace idle expiry without checking the old idle/absolute expiry, identity status or epoch. A library session expired at day 31 can be updated to a later expiry below its day-90 ceiling and resolve again. The requested expiry is capped only by absolute_expires_at, not trusted-now + configured idle duration; create has the same missing idle cap for supplied expiry. Share the guarded lifecycle with the main store or implement equivalent predicates/transaction semantics without losing the library mapping. Test direct library refresh after idle expiry, stale/disabled users, shorter configured policies and over-limit requested expiry. Preserve the original absolute ceiling and digest-only persistence.

3. **P2 — token-list filters are hashed incorrectly.** buildWhere hashes entry.value before examining operator. For a token IN list it hashes the string representation of the whole array, then hashes that digest again inside the IN branch. It cannot match any correctly stored per-token digest, so supported bulk lookup/revoke operations silently affect no rows. Branch on the operator first, hash each raw token exactly once and test supported library bulk operations against several live sessions. Do not accept a zero affected-row count as successful revoke-all; retain raw-token SQL-boundary assertions. Unsupported filter shapes must fail closed rather than broaden to an empty WHERE clause.

4. **P2 — failure/race evidence remains narrower than the R1 contract.** The new tests cover audit-insert failure, two rotations and a rolled-back successor, but do not establish commit/rollback connection-failure handling or the required rotation/revoke interleavings. A failed COMMIT acknowledgement can be ambiguous; the route comment claiming every commit failure leaves no live session is not a valid guarantee. Specify indeterminate outcome handling, never publish credentials before confirmed commit, and evict a client whose transaction/connection state is uncertain rather than swallowing ROLLBACK failure and returning it healthy to the pool. Add deterministic failure injection and real concurrent revoke/rotation checks. Preserve history and explain the permitted linearization outcome without claiming an old-token revoke necessarily reaches an already-consumed successor.

Previously corrected behavior retained: first-party login/logout same-client audit transaction; row-locked source consumption; guarded first-party refresh; 30/90-day maxima, finite integral config and strong token bounds; effective_from/effective_to validation; real-role tests and updated spy user id. The existing scrypt compatibility and no operator-password fallback remain appropriate. Future MFA, password policy, OIDC and active entry points stay out of scope.
