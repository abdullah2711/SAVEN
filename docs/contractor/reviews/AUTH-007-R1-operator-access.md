Required corrections:

1. **HIGH — subsequent admission must use the accepted lock order and fresh authority after all blocking locks.** `admitSession` takes the shared gate, samples `at`, then calls `readSessionById(...forUpdate:true)` before locking auth.users FOR SHARE. That is gate -> session -> user, despite the documented gate -> user -> session order. A reset/lifecycle transaction can hold the user while waiting for that session, while admission holds the session and waits for the user. More importantly, a credential-version update committed after the session read but before the user lock is not revalidated: the user query returns the new generation but only status is checked, and there is no locked session re-read against it. Admission can accept a credential-stale session for this request. Source expiry and mapping effective windows also use the timestamp from before these waits; an assertion that expires while blocked can still be admitted. The pause-before-exchange tests do not exercise this subsequent-admission window.

   Resolve identity without first locking the session, acquire principal/lifecycle locks in the accepted order, then re-read the exact operator session under lock and revalidate status, credential generation, revocation and local expiry. Sample trusted time after the blocking acquisitions for source/effective/assurance freshness and return that actual admission time. Apply the reviewed maximum-age/assurance ceiling to bound source-issued-at evidence where configured; storing source_issued_at but never consulting it on subsequent admission does not establish continuing freshness. Keep the mapping/role gate through the privileged operation and same owned transaction; preserve logout cleanup. Add controlled session-lock and user-lock waits with source expiry/effective-window changes, an intervening credential-generation update, and concurrent reset/lifecycle ordering. Prove invalidation-first refuses operator identity/handler/effects and admission-first has the documented serialization, with clean reuse/fail-closed cleanup. Do not weaken the customer protocol or edit applied 033.

2. **HIGH — a removed mapping can be recreated with a reused generation and revive old sessions.** `mapping_epoch` defaults to 1, and bump_access_identity_epoch advances it only on UPDATE. Neither session binding nor exchange ledger prevents deleting access_identity. Exchange a subject at epoch 1, delete that row, then INSERT the same subject/local user/operator role/assurance with defaults: the new row is again epoch 1. The still-live old binding passes issuer/audience/user/role/epoch checks, so previously removed authority can reappear without a new exchange. Shared locking serializes each operation but does not preserve mapping incarnation identity. R1 tests revocation/update and different subjects, not delete/recreation.

   Bind sessions to a non-reusable mapping incarnation/generation, or enforce retained/tombstoned mappings and a never-reused generation through the supported write protocol. Ensure ordinary supported DELETE/recreate or reassignment/return cannot resurrect earlier credentials. Preserve existing audit/source history and narrowly scoped service grants; no runtime mapping UPDATE authority is needed. Add same-subject/same-user delete/recreate and reassignment-return regressions: old sessions remain denied, a fresh authorized exchange succeeds, and unrelated subjects remain isolated. Handle any legacy binding explicitly and fail closed. Corrections can remain within the existing new 06/access/test paths; obtain an amendment before changing any other schema/file.

3. **MEDIUM — a synchronously throwing refresh callback permanently poisons the single-flight state.** In refreshOnce, the outer assignment is `refreshInFlight = (async () => { ... await refreshKeys(); ... finally { refreshInFlight = null; } })()`. A permitted non-async callback that throws before returning causes catch/finally to execute before that async invocation returns its fulfilled false promise. The outer assignment then overwrites null with that settled promise. Every future call returns it immediately, including after cooldown; key rollover can never recover until the validator is reconstructed. The regression uses an async throwing callback, which suspends through await and misses this ordering.

   Publish/retain the flight state before invoking the callback and clear it after settlement in an ordering safe for synchronous throw, rejected promise and normal return. Preserve failure cooldown, cached keys, coalescing and sanitized fail-closed responses. Add a non-async throw-once callback with an injected clock: first attempt refuses, immediate retry respects cooldown, later retry invokes the source and succeeds, and concurrent callers still coalesce. No runtime/network key fetch is required for this proof.
