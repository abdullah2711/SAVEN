With max=1, a correct login stalls waiting for itself. With a larger pool, same-scope waiters can occupy the remaining clients waiting on the first client's lock while the lock owner waits for a free client to commit success and release that lock. Distinct successful requests can also exhaust the pool this way. The current wrong-password concurrency tests never enter this branch, and the nominal restricted-role success is sequential. 2. **HIGH — partial lock acquisition, unlock failure and uncertain reservation transactions can return contaminated clients to the pool.** In `rate-limit.mjs` attempt, `await lockScopes(client, keys)` occurs before the cleanup try/finally, so failure acquiring the second scope leaks the first session lock. The final unlock suppresses errors and ignores the unlock result. Reservation COMMIT errors are followed by best-effort ROLLBACK whose failure is swallowed, then `store.withClient` always releases normally; unlike the accepted session transaction helper, this path never destroys an uncertain client. A session lock survives transaction rollback and can be inherited by a later borrower, causing hangs or same-backend reentrant admission that defeats the intended mutual exclusion. Track acquired locks from the first acquisition, confirm balanced unlocks, and destroy the connection if lock/transaction cleanup cannot be established or COMMIT outcome is uncertain. Do not release a client twice or treat a failed rollback as a reusable state. Prove second-lock failure, unlock error/false result, uncertain reservation COMMIT and failed ROLLBACK with release/destroy assertions and a subsequent uncontaminated borrower; keep no-cookie and durable-reservation ambiguity assertions. Session locks require an explicitly pinned backend across commits: document and enforce compatibility with the connection profile instead of assuming transaction-pooling middleware retains a backend. This is a session-lock lifecycle requirement, not permission to use session-level tenant context. PostgreSQL documents that session advisory locks survive rollback and are reentrant: [advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS).
