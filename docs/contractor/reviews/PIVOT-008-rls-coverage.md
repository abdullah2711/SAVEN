## Findings and required corrections

1. **HIGH — missing installed surface can produce an empty, successful coverage result.** `99-ci-rls-coverage.sql` derives every obligation from objects that happen to exist. Missing expected tables, membership, roles or functions create no violation. For example, a database containing the three empty application schemas has no covered relations/functions/policies to fail; the remaining runtime-schema checks do not establish an installed application. `verify-pg-rls.mjs --database` accepts that result. The populated-surface assertions exist only in the healthy fixture test, not in the query or CLI being certified. A missing single required table/function can likewise disappear from coverage in an otherwise populated target.

   Put the accepted installed-surface obligations at the gate boundary: identify required schemas, runtime/owner roles, relations, policy/function signatures and prerequisite installation versions, report absence explicitly, and validate compatible versions rather than minimum counts alone. Preserve extensibility by distinguishing the reviewed installed manifest from growing business domains. Test empty-schema, missing membership/table/function/role and incomplete-install targets through the actual CLI; each must fail with a specific diagnostic, while the accepted complete stack passes. Do not require only the healthy fixture to prove its own non-vacuity.

2. **HIGH — policy presence/counts do not establish the required effective isolation; runtime behavioral tests are absent.** `policy_facts` counts permissive/restrictive policies without command applicability or effective role coverage. Its expression checks only catch a literal `true` or a directly spelled `current_setting`. A SELECT-only restrictive policy can satisfy the count while INSERT/UPDATE lack the required restriction; a nonliteral always-true predicate also escapes the literal check. The same omissions affect membership. Existing negatives merely mutate catalogs and assert `coverage(db)` reports a kind; none performs an authorized or hostile tenant read/write as a restricted runtime login. They are catalog mutation self-tests, not the supplemental behavioral tests required by the contract.

   Validate the accepted effective policy contract per operation and applicable principal, including USING/WITH CHECK and restrictive admission/scope protections. Add real separate restricted-login tests with two populated tenants, valid context/authority and positive controls; prove own-tenant permitted operations, specific foreign/no-context refusals and retained data after denied mutations. Include selective command/role policies, weakened nonliteral predicates and permissive widening. A required guard removal must make the corresponding test/gate fail; restore it and show green. Match the accepted membership preselection semantics rather than inventing a new blanket policy. Do not repair catalogs in the verifier or waive this requirement as application RBAC: tenant RLS is this contract's subject.

3. **HIGH — effective forbidden grants and role assumptions are incompletely covered.** `runtime_relation_privileges` uses table/sequence checks, omitting runtime column-only ACLs; the column branch checks PUBLIC only. Thus a column SELECT on a tenant table granted to operator_read or auth_service can evade the forbidden-direct-read checks. There is no operator-to-auth table prohibition: a new operator_read SELECT on `auth.users` is material auth-boundary widening but matches none of the final cross-schema branches. Runtime function checks only prohibit customer execution of auth/operator SECURITY DEFINER functions; they do not compare each runtime's effective EXECUTE surface with PIVOT-007's accepted allow-list. Membership closure only flags role names ending migrator/definer, missing SET ROLE into an arbitrarily named privileged/bypass or other service role. Actual deployment login principals ending `_login` are not themselves runtime-classified.

   Compare effective table, column, sequence, function and role-switch authority with the accepted per-runtime profile, including associated login roles and direct/transitive membership. Check target role capabilities/ownership and cross-service authority, not merely a naming suffix; respect PostgreSQL membership SET/INHERIT semantics. Cover operator auth-record access and forbidden helper execution without granting new privileges to make tests pass. Add isolated table-versus-column grants, wrong-service function grants, arbitrary-name privileged targets and login-only privilege negatives, each with its exact violation and restricted positive control. Preserve the narrow accepted operator disclosure/audit functions and legitimate auth privileges.

4. **HIGH — reachable child/view paths are only one dependency hop deep.** `tenant_children` starts only from a parent in tenant_data; `tenant_views` only follows dependencies whose immediate referenced relation is in tenant_data (`:95–120`). A public view over a public inner view over tenant data is absent from this reachability set. If only the outer view is runtime-readable, the inner view is not flagged by the readability condition either; a bypass-owner outer projection can therefore publish tenant rows while this branch reports no violation. A multi-level inheritance chain can similarly place its reachable descendant outside the starting schema. Column-only view/child grants are also missed by table SELECT checks.

   Traverse dependencies/inheritance transitively with cycle handling, evaluate reachable runtime authority at the actual published endpoint and retain the required parent/child protections. Include nested views, materialized-view wrappers and multi-level children across schemas; test row/column grants separately, unsafe owner/invoker profiles and safe permitted paths. Do not infer safety from an intermediate object lacking a direct runtime grant.

5. **HIGH — default function ACLs and the accepted installed authority protocol are not verified.** `function_facts.public_execute` explodes only non-NULL `proacl` (`:142–146`). A NULL function ACL means PostgreSQL's default ACL, including PUBLIC EXECUTE; it does not mean no privileges. A newly introduced otherwise constrained definer function with default PUBLIC execution can evade that check. More broadly this query examines generic function flags but never checks the accepted authority/consent/policy writer-trigger bindings. Disabling one of PIVOT-007's policy/consent gates, or the accepted AUTH authority gate, leaves these catalog checks green even though PIVOT-007 expressly treats that installation as invalid. Broadening a NOLOGIN definer owner's privileges also is not equivalent to changing its login/BYPASS flags.

   Resolve effective ACL defaults, validate the accepted least-privilege owner/EXECUTE surface and reuse or equivalently enforce the accepted exact installed protocol contracts, including table/event/timing/function/predicate/firing-mode bindings and required helpers. The gate must remain read-only and fail closed, not reinstall the missing control. Test NULL/default PUBLIC EXECUTE, widened owner authority, disabled/replica-only/misbound writer gates and missing/reprofiled helpers with healthy controls. Keep accepted payload bytes unchanged; necessary new verification belongs inside existing TOUCH.

6. **MEDIUM — runner failure paths can leak its temporary database or delete an unowned collision.** `connect()` calls `fail()`/`process.exit` internally. If the second connection fails after CREATE DATABASE (`verify-pg-rls.mjs:195–199`), process exit bypasses the surrounding cleanup. Conversely any CREATE failure enters a catch that unconditionally attempts `DROP DATABASE IF EXISTS` on the chosen name (`:202–205`), without establishing this run created it. Random naming reduces collision probability; it is not ownership evidence. Drop/connection cleanup errors in this catch are swallowed, so the operator loses residue evidence.

   Make inner operations throw and centralize exit after owned-resource cleanup. Track confirmed ownership, distinguish failed/uncertain creation from a pre-existing name, never drop an unowned database, and preserve primary plus cleanup failures with the retained target identified. Add deterministic name-collision, post-create connection failure and cleanup-failure probes, proving pre-existing objects remain and owned residue is either removed or explicitly reported. Retain dedicated-cluster opt-in and never target production/client databases.
