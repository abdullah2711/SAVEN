Required corrections:

1. **HIGH — active GL includes unposted sources.** In 042, `active_general_ledger` joins journal lines/headers and only excludes an existing entry_voids row. It never requires the source command to be POSTED. Committed accepted/pending/failed source rows can therefore affect balances before posting; the “races” test even describes an accepted-but-unposted journal as staying active. Join the actual source command lifecycle and include only effectively posted, nonvoided journals. Preserve historical POSTED receipts after void. Test independently committed unposted/incomplete, failed/rejected, posted and VOIDED sources under the customer role, with exact active totals and retained void history. An incomplete source must never enter active balances merely because it lacks a tombstone.

2. **HIGH — action checking invents a permission shape and bypasses existing business controls.** 042 checks a top-level boolean `permissions['accounting.entry.void']`, while retained role permissions use `actions` plus company/branch/account scopes, maxMinor and review. Tests seed the invented shape. Explicit denials, resource scope and approval requirements are not checked; policy/approval versions are caller-supplied annotations, not verified bindings. Locked periods are observed but always allowed. D-014 defers fine-grained READ visibility; it does not waive delete authority, period or approval policy. Preserve the canonical permission/reference contract and a verified, version-bound policy decision through a reviewed interface; keep configurable business rules out of RLS. Denied/unknown/stale action or policy decisions must fail closed. Until an authorized closed-period workflow exists, merely recording period_locked=true is insufficient to override a lock. Test canonical action grants, explicit deny, out-of-company/branch/account/amount scope, missing/stale approval and period restrictions. Normal module readers must retain role-agnostic void-history access. The runtime denial-log INSERT must also bind its recorded actor/UUID to verified context rather than accepting arbitrary actor fields as trustworthy security evidence.

3. **HIGH — source/dependency races and concurrent replay are not protected.** The void-only advisory lock is not taken by posting or child/correction inserts. 040 child guards read state without a shared serialization protocol: a child insert can observe a nonfinal command, wait uncommitted while another transaction posts, then commit late. `journal_corrections` has no dispatcher guard at all; a correction can be attached after void or race the dependency check and leave an active reversal against an excluded original. Serialize all relevant writers/checks with consistent locks and commit-time invariants, including both ends of correction references, without mutating retained payloads. Also recheck idempotency after obtaining the lock: two simultaneous same-key calls currently both miss the initial lookup, then the loser raises ENTRY_ALREADY_VOIDED rather than replaying the same receipt. Define same-key/different-entry conflict behavior and canonical request binding. The named race test contains sequential awaits/savepoints, not concurrent transactions. Add controlled two-connection tests for late-line/evidence versus post, correction versus void, same-key replay, distinct duplicate void and void versus posting, with exact final rows/audit/outbox totals. Advisory locks only coordinate writers that participate in the protocol; see [PostgreSQL locking](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS).

4. **HIGH — nominal posting is not proven executable by the runtime role.** 040 revokes PUBLIC execution of `immutability_040_assert_posted_effects` but never grants it to saven_customer_app. The invoker command trigger calls that helper on transition to POSTED; runtime posting therefore encounters a nested function EXECUTE denial. The tests seed/post every journal through adminQuery, masking the runtime path. Grant only the required helper authority or use another reviewed constrained design, then prove accepted -> effects -> POSTED as the actual customer role and reject missing audit/outbox, imbalance and invalid operational effects. Extend the current weak “stock operation has any movement”/trade checks to the required reconciled supported effects, or explicitly fail unsupported shapes before POSTED. Preserve native pending/rejection/correction and numbering behavior; a static function-name assertion is not financial parity. PostgreSQL function execution is an explicit privilege: [GRANT](https://www.postgresql.org/docs/18/sql-grant.html).

5. **HIGH — the reused definer authority is not validated completely and grants exceed the demonstrated minimum.** 042 checks role flags, memberships and some ownership, but accepts pre-existing schema CREATE/table/function/column/sequence/default privileges and database/tablespace ownership outside that checked surface. It grants full-row SELECT across many tables, including unused trade_documents, and broad INSERT rather than an enumerated column minimum. This is weaker than the accepted dedicated-admission-owner boundary. Validate the complete allowed authority before and after changes and ownership transfer; refuse incompatible reused roles transactionally, preserving their prior bytes/metadata. Narrow each grant to actual primitive/trigger dependencies and prove no runtime can assume the role and no auth/operator/DDL path appears. The schema-wide REVOKE sweeps must not silently repair/remove unrelated prior grants; refuse unexpected authority or scope changes explicitly. Add polluted-owner negative fixtures for extra ACLs, CREATE, ownership, default privileges and membership paths, plus rollback preservation and actual runtime positives. Offline administrator provisioning of a non-login owner is acceptable in principle; it is not permission for a privileged runtime or an unvalidated reused owner.

6. **HIGH — runtime exposure precedes installation of the protections.** 040 and 042 create guard functions without attaching them; 042 commits runtime EXECUTE/read/denial INSERT grants before the separate 40 dispatcher transaction installs any trigger. Stop after step 11 of the documented run order: the void primitive is callable while terminal/audit/source guards are not yet active. Direct runtime command mutations also remain possible in that interval. Make installation/activation atomic or explicitly fail-closed until all required guard bindings are verified; a clean fixture that runs every file before yielding does not prove this. Test interrupted install, failed dispatcher registration and upgrade with existing rows, not only dispatcher rerun. Preserve applied payload bytes and every required protection; no destructive migration or generic latest-only dispatch. Complete canonical VOIDED/action reference registration rather than claiming compatibility solely from inline comments; the contract now permits the bounded canonical JSON addition.
