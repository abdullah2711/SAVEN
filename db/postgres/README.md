# PostgreSQL target schema — operator, auth and tenant bootstrap

This directory is the new PostgreSQL target for the controlled pivot. SQLite remains the production path until the retirement gate in `docs/pivot-notes/01-adr-postgresql-pivot.md` is satisfied. It creates constrained roles, Purpose A operator controls, the canonical `auth` identity schema, the Purpose B/C `tenant_data` tables, (PIVOT-004) forced tenant row-level security with atomic least-privilege runtime grants, (PIVOT-005) retained posted sources and terminal void guards, (PIVOT-006) append-only actor-bound tenant change audit, and (PIVOT-007) the audited, customer-granted operator read boundary: a versioned read policy, consent-serialization triggers, three `SECURITY DEFINER` functions (two runtime, one internal protocol validator) owned by `saven_operator_definer`, and the `src/operator/support-read.mjs` publishing adapter, plus (PIVOT-008) the read-only RLS/privilege coverage gate (`99-ci-rls-coverage.sql` + `scripts/verify-pg-rls.mjs` + `check.mjs --postgres`). It does **not** create a login flow, an MFA flow, an application route or any provider connector. Tenant data is still not safe to serve: AUTH-006 (verified tenant context), auth-side forced RLS and the posting kernel remain open.

## Run order

1. `db/postgres/00-roles.sql` — creates constrained NOLOGIN roles. It validates every existing target role first; incompatible pre-existing definitions cause an explicit refusal before mutation. Compatible existing roles are a no-op and are never altered. Run with the private migration/admin connection.
2. `db/postgres/10-operator-schema.sql` — creates the `operator` schema, Purpose A tables, grants, indexes and append-only triggers. The executing connection must be a member of `saven_migrator` (or a superuser). DDL objects are owned by `saven_migrator`.
3. `db/postgres/05-auth-schema.sql` — creates the canonical `auth` schema: identity, provider bindings, tenant membership, sessions, verification, two-factor, recovery codes, assurance roles, append-only auth audit and OAuth readiness. Same membership requirement and ownership rule as step 2.
4. `db/postgres/migrations/006-auth-schema-corrections.sql` — additive AUTH-001 correction applied after `05`. It adds and validates `oauth_state_pkce_key_binding_chk`; the delivered `05` bytes are never edited.
5. `db/postgres/20-tenant-schema.sql` — creates the `tenant_data` schema and its Purpose B/C tables, composite tenant keys, exact money columns, reference/rule tables and the canonical pending-document sidecars. Same migration principal and ownership rule as step 2. Rerunning it is intentionally refused: later changes are additive files under `db/postgres/migrations/`, never an in-place edit of an applied migration.
6. `db/postgres/migrations/021-tenant-schema-corrections.sql` — additive PIVOT-003 correction applied after `20` (see the tenant section below).
7. `db/postgres/30-rls-policies.sql` — PIVOT-004: adds the constrained canonical-principal projection, forces row-level security on all tenant tables, creates the isolation and admission policies and grants the runtime its per-table privileges, all in one transaction. It requires `00`, `05`, `10`, `20` and `021` to have been applied and refuses to run on a partial stack.
8. `db/postgres/migrations/031-rls-corrections.sql` — PIVOT-004-R1, applied by the **separate offline administrator (superuser)**, not by the migration login: it provisions the `saven_tenant_admission_definer` NOLOGIN role, transfers only the admission function to it, enables forced membership isolation on `auth.tenant_membership` with two principal-bound policies, completes the represented company foreign keys and replaces the blanket runtime sequence grant. It refuses a second application and runs as one transaction.
9. `db/postgres/migrations/032-rls-hardening.sql` — PIVOT-004-R2, also applied by the offline administrator: it first validates the admission owner's **full authority surface** against an exact allow-list and refuses (rolling back) on any excess, then adds the restrictive membership guards that stop an extra permissive policy from widening preselection or the admission lookup. It changes no privilege and is refused on re-application.
10. `db/postgres/migrations/040-posted-immutability.sql` — PIVOT-005 payload 040 (applied by a member of `saven_migrator`): trigger functions that protect retained posted sources, children, evidence, numbering and drafts, bind accepted receipt actors to verified context, constrain approval transitions and protect both ends of correction links. It attaches no trigger by itself and is immutable; a second application is refused. Its posting boundary is the plain balanced journal; operational trade/stock shapes fail closed until a reviewed reconciliation workflow exists.
11. `db/postgres/migrations/041-audit.sql` — PIVOT-006 payload 041, applied by the **offline administrator (superuser)**: provisions the dedicated constrained `saven_audit_definer` NOLOGIN owner and installs the append-only actor-bound tenant change audit writer, the native-audit insert guard, the versioned secret-safe serializer/provenance helper and the audit-table append/TRUNCATE guards. It defines functions only (no trigger attachment) and is immutable; a second application is refused. The audit owner has only enumerated member/reference mapping reads, audit_event column INSERT, identity-sequence access and the narrow context/admission helper calls; it owns only the reviewed audit-writing/actor-binding functions, has no business-table write, table/schema ownership or broad auth/operator read, and grants the runtime nothing. The complete authority surface is validated against an exact allow-list and a polluted pre-existing role is refused rather than repaired.
12. `db/postgres/migrations/042-entry-voiding.sql` — PIVOT-005 payload 042, applied by the **offline administrator**: creates the append-only `entry_voids` record (including exact approver/decision metadata) and `void_denials` log, the canonical `active_general_ledger` and `voided_entries` projections, the atomic void primitive and its narrow `saven_void_definer` owner, plus payload 042 guards. It grants the runtime **nothing**; role-agnostic (no business role name, eligibility class or void-specific read restriction); refused on re-application.
13. `db/postgres/40-triggers.sql` — the explicit dispatcher **and activation step**. It attaches every registered payload guard (040, 041 and 042, including the deferred commit-time correction constraint), refuses a missing or unregistered payload, and only then grants the runtime interface (`void_posted_entry`, the canonical projections, the denial log) after verifying the guards are attached. It attaches the 041 audit writer to the reviewed business table list and the append/TRUNCATE guards to `audit`/`audit_event`. A partial install therefore never exposes the void command and never leaves an audited business table unguarded. Run it after each payload; re-running is safe and never reapplies a payload. PIVOT-006 registers 041 here alongside 040/042 without editing their bytes. If 041 is not installed, a 040/042-only installation remains runnable and explicitly does **not** claim PIVOT-006 audit coverage; PIVOT-006 acceptance requires the 041 payload.
14. `db/postgres/50-functions.sql` — PIVOT-007 payload, applied by the **offline administrator (superuser)**: it provisions no role (the seven-role bootstrap already creates `saven_operator_definer`), creates the versioned `operator.access_read_policy`, the consent-writer and policy-writer gates with their nine `support_grants`/`members`/`access_read_policy` triggers, `operator.read_tenant_support()`, `operator.log_operator_read_denial()` and the internal `operator.assert_read_authority_protocol()`, revokes the broad bootstrap operator grants from the definer and re-grants only the enumerated minimum, transfers the three functions, and validates the complete definer authority surface plus the EXECUTE allow-list. It is additive, grants no tenant table to an operator runtime, and is refused on re-application. Run it after `30` and AUTH-007 `06`; the deployment must then seed `operator.access_read_policy` or every read fails closed.
15. `db/postgres/99-ci-rls-coverage.sql` — PIVOT-008. This is **not a migration and is never applied to the database**: it is a read-only catalog query that must return zero rows. The operator runs it after the full stack, and `scripts/verify-pg-rls.mjs` translates a non-empty result into a nonzero process exit. It performs no DDL, DML, grant or repair.

Migrations under `db/postgres/migrations/` are additive corrections applied after their base file, in numeric order, with the same principal. They never rewrite a delivered base SQL file, and they validate existing data instead of repairing it.

No password, connection string, DSN or login principal is stored in these SQL files. Runtime services authenticate separately and use `SET ROLE` only after their own server-side authorization checks. Runtime logins must be separate from the offline migration login; only that migration principal may assume `saven_migrator`.

## Auth identity schema (AUTH-001)

`auth` is the canonical identity and authentication authority for both profiles; Fully Private keeps this schema rather than a vendor-only variant. It is schema-only: no login route, session service, MFA flow, recovery flow, provider connector or OIDC exchange exists yet, and no installed library is activated by these tables.

| Table | Purpose |
| --- | --- |
| `auth.users` | Canonical identity. `legacy_id` preserves the original native text id uniquely; `password_hash` stores only an opaque PHC verifier with `password_scheme` (retained scrypt, preferred Argon2id); `credential_version` invalidates older sessions. |
| `auth.accounts` | Unique `(provider_id, account_id)` provider binding. Provider tokens exist only as ciphertext bound to a key version. Passkey activation requires its own plugin schema and is not present. |
| `auth.tenant_membership` | Sole tenant admission authority: `tenant_id`, `user_id`, `role_id`, `status`, `membership_epoch`, invitation/acceptance timestamps. |
| `auth.sessions` | Server-side sessions. Only SHA-256 hex digests of opaque tokens are stored; idle and absolute expiry with an immutable absolute ceiling. |
| `auth.verification` | Expiring, single-use email-verification/password-reset challenges stored as digests; consumption is one conditional `UPDATE`. |
| `auth.two_factor` | TOTP factors with an encrypted recoverable seed, algorithm and key version; `last_used_step` records replay refusal. |
| `auth.recovery_codes` | One-way hashed, atomically single-use MFA recovery codes. |
| `auth.auth_audit` | Append-only authentication event history; `UPDATE`, `DELETE` and `TRUNCATE` are refused for every role including the owner. |
| `auth.oauth_state` | Expiring, single-use OAuth state/nonce/PKCE readiness; no provider is configured or contacted. |
| `auth.roles`, `auth.reference_value` | Authentication-assurance classes and effective-dated auth domains as data, not code constants. |

Auth boundaries:

- `auth.tenant_membership` is tenant-scoped. AUTH-001 ships no RLS, but forced membership isolation and per-table isolation policies remain mandatory in PIVOT-004/PIVOT-008; nothing here exempts membership from that gate.
- There is no foreign key from `auth.tenant_membership.tenant_id` to `operator.tenant`: Fully Private omits vendor operator tables. PIVOT-004 adds the stored tenant-member UUID projection and the exact UUID/text/membership constraints.
- Customer and operator roles have zero `auth.*` privileges. `saven_auth_service` holds lifecycle `SELECT, INSERT, UPDATE` and audit `SELECT, INSERT` only — no `DELETE`, `TRUNCATE` or DDL. `saven_auth_definer` is read-only plus audit `INSERT`.
- Passwords, session tokens, verification tokens, recovery codes and OAuth state are never stored in plaintext; recoverable secrets (TOTP seeds, provider tokens, PKCE verifiers) are ciphertext with an algorithm and key version.
- The additive correction `006-auth-schema-corrections.sql` closes the nullable PKCE key binding: a ciphertext now requires a non-null positive key version, and validation refuses invalid pre-existing rows rather than repairing them.

## Purpose B/C tables (PIVOT-003)

`20-tenant-schema.sql` creates one shared `tenant_data` schema with 47 tables. Every table, including children and rule tables, carries `tenant_id uuid NOT NULL` as its leading column, leads its primary key with `tenant_id`, and scopes every foreign key, unique key and document-number key by `tenant_id` (plus the existing company/branch components where the source had them). No cross-schema foreign key is created in this file, and PIVOT-003 applies identically whether or not AUTH-001 has landed. `tenant_data.members.user_id` preserves the native text principal id; the text-to-UUID mapping and the composite `(tenant_id, …)` link to `auth.tenant_membership` are finalized in PIVOT-004. A foreign key to vendor `operator.*` is not planned for `tenant_data`: the Fully Private composition omits those tables, so the tenant UUID is validated by the operator/tenant service contract instead.

| Group | Tables |
| --- | --- |
| Identity projection, masters, periods | `business`, `members`, `roles`, `assignments`, `denials`, `accounts`, `account_profiles`, `periods` |
| Accepted commands, approval, ledger | `command_inbox`, `approval_requests`, `journals`, `journal_lines`, `audit`, `outbox`, `document_sequences`, `document_numbers`, `journal_drafts`, `command_decisions` |
| Company, inventory, evidence | `company_profiles`, `warehouses`, `stock_items`, `stock_balances`, `stock_operations`, `stock_movements`, `company_settings`, `command_files`, `inventory_controls`, `journal_corrections` |
| Trade subledger | `trade_controls`, `trade_parties`, `trade_operations`, `trade_documents`, `trade_lines`, `trade_allocations`, `trade_credits`, `trade_credit_lines` |
| Provenance and configuration | `source_store_migrations`, `reference_values`, `business_rule`, `approval_policy`, `posting_constraint`, `tax_profile`, `support_grants` |
| Audit and pending-document sidecars | `audit_event`, `document_registry`, `document_revisions`, `verified_entitlement` |

Compatibility rules applied to every table:

- Source table and column names are preserved exactly. Text ids stay `text`; an existing alpha/northstar id is never cast to `uuid`. The tenant UUID mapping remains `operator.tenant.legacy_id`.
- Native integer minor units stay `bigint` with the same bounds (`0..999999999999`, or `> 0` for document and line amounts). No `real`, `double precision` or `money` column exists anywhere.
- Native epoch-millisecond integers stay `bigint` epoch milliseconds so imported values remain comparable with the native stores. Native ISO date text (`posting_date`, `start_date`, `end_date`, `due_date`) is preserved as text.
- Native `INTEGER` 0/1 flags become `boolean`; the adapter performs that lossless mapping.
- Purpose C policy tables have no native source, so they use `timestamptz`, exact `numeric` decimals and a JSON-schema version column.
- PIVOT-003-R1 restores the native stock valuation invariant on `tenant_data.stock_balances`: `CHECK (quantity > 0 OR value = 0)`, added as the validated named constraint `stock_balances_quantity_value_chk`, so an empty balance can never retain owned stock value. Native parity is preserved rather than deferred to PIVOT-005/013.
- `tenant_data.tax_profile.tax_type` defaults to the canonical seeded `SALES_TAX` value; a default must always resolve to its reference domain instead of an unseeded label.
- Configurable rule data stays inert. `posting_constraint.rule_jsonb.severity` is governed by the `posting_constraint_severity` reference domain (effective-dated `tenant_data.reference_values` rows, interpreted only by the registered handler named in `handler_key`); it is not a JSON-schema enum, and a new value can never install executable policy.
- Growing domains (command state, document type/status, party kind, origin type, action type, ...) are **not** `CHECK` lists. They are declared reference domains annotated inline as `reference domain: <name>` and seeded canonically in `contracts/postgres-business-rules-v1.json`. A new value is a `tenant_data.reference_values` row, not a migration. Only structural/accounting invariants (money bounds, debit/credit exclusivity, positive amounts, one protected ultimate-owner role, one ultimate-owner assignment) are enforced by `CHECK`/unique constraints.
- `tenant_data.document_registry` and `tenant_data.document_revisions` are the canonical pending-document sidecars. AI-origin documents are ordinary documents whose status is `PENDING_APPROVAL` with origin metadata; there is no `ai_proposal` table. Accepted command bytes in `command_inbox` stay immutable and are never rewritten by a pending edit.

Forced RLS, policies, runtime grants and the canonical-principal projection are added by `30-rls-policies.sql` (PIVOT-004, next section). Still deferred, and absent from the tenant base file: posted-source immutability triggers (PIVOT-005), business audit triggers (PIVOT-006), verified application context (AUTH-006) and the posting kernel (PIVOT-013). Additive corrections land as `db/postgres/migrations/*.sql` after their base file; this directory currently carries `006-auth-schema-corrections.sql` and `021-tenant-schema-corrections.sql`.

## Tenant isolation, policies and runtime grants (PIVOT-004)

`30-rls-policies.sql` is one transaction: the constrained principal projection, `ENABLE`/`FORCE ROW LEVEL SECURITY`, the policies and the runtime grants land together, so no committed state exposes tenant rows without isolation.

**Context.** Isolation reads two transaction-local GUCs, `app.current_tenant_id` and `app.current_user_id`. They are set by the application's tenant-context middleware (AUTH-006) with `select set_config('app.current_tenant_id', $1, true)` inside the request transaction, from a verified server-side session plus an explicit membership check. The database never derives the tenant from a header, query parameter, body field or session-level `SET`, and a pooled connection cannot inherit one request's tenant into the next. Absent, empty or malformed context yields `NULL` and therefore denies; it does not raise, so a missing context is a clean zero-row/refused-write outcome rather than an error oracle.

**Policies.** Every `tenant_data` table carries three policies:

| Policy | Kind | Applies to | Predicate |
| --- | --- | --- | --- |
| `<table>_tenant_isolation` | PERMISSIVE | all roles | `tenant_id = current tenant` |
| `<table>_tenant_scope` | RESTRICTIVE | all roles | `tenant_id = current tenant` |
| `<table>_runtime_admission` | RESTRICTIVE | `saven_customer_app` | `tenant_id = current tenant AND session_admitted(tenant, user)` |

The duplicated tenant predicate is deliberate. Permissive policies are OR-ed and restrictive policies are AND-ed, so a later permissive policy (including a mistaken `USING (true)`) cannot widen visibility or writes past the tenant scope, and the admission guard cannot be bypassed by an extra permissive policy either. `FORCE` means the table owner is subject to the same tenant scope: the offline migration role does not silently read across tenants, and `SET row_security = off` is refused rather than granting a bypass. RLS is isolation only: approval, amount, branch, resource and role policy stay in application/business validators.

**Admission.** `tenant_data.session_admitted(tenant, user)` is a `STABLE SECURITY DEFINER` function returning a boolean only. It requires an active `tenant_data.members` row, an active `auth.tenant_membership` (`status = 'active'`, no `suspended_at`, no `revoked_at`) and an active `auth.users` row. It exists because the runtime holds no `auth.*` privilege and must not be granted one just to satisfy a policy; the body is fixed, schema-qualified, has `search_path = pg_catalog, auth, tenant_data`, contains no dynamic SQL and exposes no document, credential or session data. `EXECUTE` is revoked from `PUBLIC` and granted only to `saven_customer_app`. `031-rls-corrections.sql` moves ownership from the offline DDL role to the dedicated `saven_tenant_admission_definer` (NOLOGIN, no superuser, no `BYPASSRLS`, no `CREATEROLE`, no inheritance, no runtime membership), which holds only column-level reads on `auth.tenant_membership`, `auth.users` and the `tenant_data.members` projection plus `EXECUTE` on the two context helpers. `032-rls-hardening.sql` then validates that owner's **complete authority surface** before and after adding the membership guards: role flags, direct and transitive memberships (no outbound path, no SAVEN principal that can assume it), object ownership (only the one function), schema ACLs (exactly `USAGE` on `auth` and `tenant_data`, no `CREATE` anywhere, no `operator` access), empty table/sequence ACLs, exactly ten column-level `SELECT` grants, exactly the two helper `EXECUTE` grants plus the owner's own entry, no default-privilege path, and no database/tablespace ownership. Any deviation refuses the migration and rolls back; nothing is revoked or "repaired", so an operator must investigate a reused role rather than have unrelated grants silently stripped. The helper also binds its arguments to the verified transaction context, so a runtime that can call it cannot use it to probe arbitrary (tenant, user) pairs; an arbitrary-pair call returns false.

**Principal projection.** `tenant_data.members` keeps the native text `user_id` and adds `user_uuid uuid NOT NULL`, a constrained projection of the canonical identity, never a second identity registry. Three constraints bind it: `UNIQUE (tenant_id, user_uuid)`, `FOREIGN KEY (tenant_id, user_uuid) → auth.tenant_membership (tenant_id, user_id)` and `FOREIGN KEY (user_uuid, user_id) → auth.users (id, legacy_id)`, which requires the additive pair key `auth.users (id, legacy_id)`. Text and UUID identity therefore cannot diverge: a mismatched pair, a dangling UUID or a renamed legacy id under a bound principal is rejected by the database. FK existence is not admission; the `session_admitted` check above still requires active status.

**Grants.** `saven_customer_app` is the only direct tenant runtime grantee. Grants are per table, not blanket, and are atomic with the policies:

| Class | Privileges | Tables |
| --- | --- | --- |
| Accepted/immutable sources | `SELECT, INSERT` | `journals`, `journal_lines`, `trade_operations`, `trade_documents`, `trade_lines`, `trade_allocations`, `trade_credits`, `trade_credit_lines`, `stock_operations`, `stock_movements`, `command_decisions`, `command_files`, `document_numbers`, `document_revisions`, `journal_corrections` |
| Command receipt | `SELECT, INSERT` + column `UPDATE (state, lease_token, lease_until, error, approved_by, updated_at, updated_by)` | `command_inbox` |
| Native command audit | `SELECT, INSERT` (no `UPDATE`/`DELETE`) | `audit` |
| Trigger-only evidence | `SELECT` only | `audit_event` |
| Provenance | `SELECT` only | `source_store_migrations` |
| Mutable business/configuration | `SELECT, INSERT, UPDATE` | `business`, `members`, `accounts`, `account_profiles`, `periods`, `approval_requests`, `outbox`, `journal_drafts`, `company_profiles`, `company_settings`, `warehouses`, `stock_items`, `stock_balances`, `trade_parties`, `reference_values`, `business_rule`, `approval_policy`, `posting_constraint`, `tax_profile`, `support_grants`, `verified_entitlement`, `document_registry`, `document_sequences` |
| Administration | `SELECT, INSERT, UPDATE, DELETE` | `roles`, `assignments`, `denials`, `inventory_controls`, `trade_controls` |

No runtime `TRUNCATE`, `REFERENCES`, `TRIGGER`, schema `CREATE` or table ownership is granted. `audit_event` is written by PIVOT-006 triggers only, so the runtime cannot forge change evidence, and posted/accepted sources are append-only by privilege before the PIVOT-005 triggers exist. `saven_auth_service`, `saven_auth_definer` and every operator role hold no tenant privilege and no tenant policy addresses them; `PUBLIC` holds nothing.

**Membership isolation (PIVOT-004-R1/R2).** `auth.tenant_membership` has `ENABLE` + `FORCE ROW LEVEL SECURITY` with a permissive/restrictive pair per privileged role, all role-scoped, non-`PUBLIC` and non-blanket:

| Policy | Kind | Role | Predicate |
| --- | --- | --- | --- |
| `tenant_membership_preselect` | PERMISSIVE | `saven_auth_service` | `user_id =` the verified user in transaction context (`app.current_user_id`) |
| `tenant_membership_preselect_scope` | RESTRICTIVE | `saven_auth_service` | same predicate |
| `tenant_membership_admission_lookup` | PERMISSIVE | `saven_tenant_admission_definer` | `(tenant_id, user_id) =` the verified transaction context pair |
| `tenant_membership_admission_scope` | RESTRICTIVE | `saven_tenant_admission_definer` | same predicate |

The restrictive partners exist because permissive policies are OR-ed: without them, one added `PERMISSIVE … USING (true)` for a role that already has membership access would expose every principal's membership rows. With the pair present, the restrictive predicate is AND-ed with any permissive policy, so preselection stays bound to the verified user and the admission lookup to the verified pair. `032-rls-hardening.sql` adds these guards and supersedes the earlier permissive-only expectation; `30-rls-policies.sql`'s tenant-table model already used the same permissive+restrictive shape.

Preselection is the login path: after credential/session verification the auth service sets `app.current_user_id` for the transaction and reads that user's memberships, including memberships in several tenants, so tenant selection is still possible before any tenant is chosen. It never sees another principal's rows, and an unset, empty or malformed context returns none. The admission lookup sees exactly one pair. Neither predicate calls a `tenant_data` policy helper, so there is no recursion path, and the policies are permissive-only-by-role with no `USING (true)`. Membership *writes* (invitation, acceptance, role change) have no policy here: they fail closed until the contract that implements them adds a narrow policy bound to the verified inviter/administrator principal. That is deliberate, not an omission to be worked around with a grant.

`auth.users` and `auth.sessions` are global principal and service records, not tenant-scoped rows. They keep their own principal/service authority and are deliberately not given blanket tenant policies here; their isolation is a separate AUTH-boundary concern, and no auth table is granted to the tenant runtime.

**Scoped references (PIVOT-004-R1).** A valid tenant context does not establish a valid company, so these represented company columns now have a parent: `journals.company`, `periods.company`, `journal_drafts.company`, `document_registry.company` (nullable), `trade_controls.company` and `trade_parties.company` → `tenant_data.company_profiles (tenant_id, id)`. Each was added `NOT VALID` and then validated, so incompatible pre-existing rows fail loudly. The remaining relationships are application-level by design and are inventoried rather than silently ignored:

| Relationship | Why it is not a database foreign key |
| --- | --- |
| `command_inbox.payload`, `journal_drafts.payload`, `document_revisions.payload`, `stock_operations.payload`, `trade_operations.payload` company/branch fields | They live inside versioned JSON payload bytes. Rewriting or parsing them into columns would break the preserved accepted bytes and the pending-revision contract. The posting kernel validates them against `company_profiles` before posting. |
| `branch` strings (`journals.branch`, `periods` has none, `warehouses.branch`, `trade_controls.branch`, `trade_parties.branch`, `trade_documents.branch`, `document_registry.branch`) | The accepted schema has no branch master table; a branch is a free-form label in the native source. Adding one would invent a schema the contracts do not define. |
| `trade_documents.company/branch` | Already constrained transitively by its composite party foreign key, which includes tenant, company and branch. |

Lookup indexes back the new parents: `journals (tenant_id, company)`, `journal_drafts (tenant_id, company)`, `document_registry (tenant_id, company)`, plus `assignments (tenant_id, role_id)` from PIVOT-004.

**Sequence privilege.** The runtime no longer holds `USAGE, SELECT` on every tenant sequence. It keeps `tenant_data.audit_id_seq` (the only identity it inserts through) and the trigger-only `audit_event_id_seq` is withheld, so change-event evidence cannot be minted by the runtime. New sequences require an explicit grant.

## Posted-source retention and terminal void (PIVOT-005)

Posted accounting sources are physically retained and immutable, and an authorized user can remove a posted entry from the active ledger by an **atomic terminal void**. This follows the owner decision D-013 and the role-agnostic correction D-014; the database does not decide which business roles may see voided entries.

| Object | Purpose |
| --- | --- |
| `tenant_data.entry_voids` | Append-only void record. `UNIQUE (tenant_id, entry_id)` makes exactly one terminal void possible; the row carries actor (text id plus canonical UUID), reason, original/effective state, source digest and version, line count, request digest, idempotency key, correlation/policy/approval versions, the exact independent approver and approved decision digest, period-lock snapshot and void time. Never updated or deleted. |
| `tenant_data.void_denials` | Append-only denial log. A denied void raises and therefore cannot write its own audit row; the application records the refusal here in a separate transaction. The payload guard overwrites the actor fields from verified context. |
| `tenant_data.active_general_ledger` | Canonical active-GL projection: every line of a journal whose accepted command is effectively `POSTED` and which has no void record. Unposted, accepted, pending, failed or rejected sources never affect balances. Consumers (balances, trial balance, reports, exports, search) must use this inclusion rule rather than filtering registers ad hoc; a voided journal keeps its historical POSTED receipt. |
| `tenant_data.voided_entries` | Canonical Deleted/Voided projection: the original posting plus the retained void record, exact approver metadata and void time. |
| `tenant_data.void_posted_entry(...)` | The single atomic primitive. Under the shared per-command advisory lock plus an idempotency-key lock it re-verifies transaction context, actor mapping, the canonical role-permission decision (`actions`, company/branch/account scope, `maxMinor`, `review`), explicit denials, the currency-matched effective approval policy, posted state, locked periods and the supported dependency graph. Review-required voids need a pre-registered command whose full submission matches, an `APPROVED` request bound to the exact accepted digest and canonical decision, and an independent approver whose current membership and `journal.approve`/resource authority are revalidated at execution. It writes receipt, native audit, change audit, outbox and void record in one transaction and replays an identical request without a second event. |

Approval semantics are explicit and fail closed. A request is created `PENDING`; only the verified approver may transition it to `APPROVED`, its `decided_by` and bound digest are immutable, and a direct `APPROVED` insert or a requester stamping another member's id is refused. The approver must be an active, independent member with `journal.approve` (or protected-owner) authority and must not hold an explicit denial.

Approver authority is resource- and amount-complete. `immutability_040_approval_resource` resolves company, branch, accounts and exact minor-unit amount from the authoritative void target, the command journal, or the immutable accepted payload (including a pending accepted command that has no journal yet). Missing, incomplete or malformed resource data fails closed; there is no action-only fallback. Unsupported command shapes also fail closed until a later reviewed adapter defines their canonical resource. A single role must independently cover the action, company, branch, **every account**, and the **`maxMinor` ceiling**; malformed present limits/scopes fail closed, and scopes from unrelated roles are never combined into a broader grant. The same helper is used at the approval transition and re-run by the void primitive at execution, so an approver narrowed after approval (account or amount) cannot execute. At execution the exact submission (actor, digest, entry, reason, request digest, correlation), the approved canonical decision and the approver's current membership/authority are rechecked; fabricated, revoked, self, wrong-submission and stale approvals are refused. `entry_voids.approval_version` records the real policy version, never a constant.

Policy selection is role-applicable, identity-versioned, deterministic and unit-explicit. Policies are filtered by action, currency, effective dates and the requester's **matching current role identities**. A role-specific policy overrides the global policy for that role; a matching role with no specific policy falls back to the global policy. Versions belong to a `(policy_key, role scope)` identity: the current effective version is resolved **within each identity first**, then every applicable current identity in the selected scope is combined conservatively. The lowest threshold controls review and any different-approver requirement wins. Version numbers are never priority across policy keys, so unrelated or higher-version high-threshold keys cannot mask a required review. `approval_threshold_amount` is interpreted as exact **minor units** of the policy currency for this terminal-void action only (no lossy decimal conversion and no hardcoded currency-exponent table); a non-integral, negative or out-of-bound value is invalid. The decision binds the ordered matching role ids plus every selected identity/scope/version/currency/threshold, the amounts, entry and request digest, so a role or policy change after approval makes it stale.

Terminal rules enforced by the database: a voided entry cannot be edited, unvoided, physically deleted or deleted twice; the source journal, lines, command receipt, evidence and permanent numbers stay byte-for-byte retained; no late lines, evidence, movements or decisions may be attached after posting; void audit rows are immutable under both the 042 void guard and the generic 041 append-only guards.

Correction references protect **both** ends. `journal_corrections` takes the shared advisory lock for the original and the reversal in one deterministic order, requires a posted non-voided original and a non-final, non-voided reversal, and is immutable. The native accept-then-execute flow is preserved: a link is created while the reversal is pending and the deferred commit check revalidates both ends at commit. A late link onto a posted or already voided reversal is refused, and neither end of a linked correction can be voided as a plain journal.

Read and delete authority are separate mechanisms: normal module access reads the projections (tenant/company/branch scope still applies), while executing the void requires the action key independently. Fine-grained visibility of Voided Entries is intentionally **not** a database rule (D-014): no eligibility column, role-name predicate or category-specific denial exists in 042. A future application RBAC / User Access Settings phase owns that policy and must apply it consistently to pages, APIs, search, exports and AI tools.

Supported posting and void dependency graph for this increment is the plain journal. `assert_posted_effects` refuses any command carrying trade or stock operational rows before `POSTED` (`POSTED_OPERATION_UNSUPPORTED`); it does not claim shallow existence checks are reconciliation. Retained/imported operational rows are likewise refused by the void primitive (`VOID_DEPENDENCY_UNSUPPORTED`) and journals that are one side of a posted correction are refused (`VOID_LINKED_CORRECTION`), always with no partial effect. Broader dependency reconciliation is a later reviewed operational workflow (PIVOT-013). Voiding does not undo physical stock movement or customer custody, and period-lock state is captured for attribution rather than silently rewriting history.

Reference registration: `VOIDED` and the action keys `accounting.entry.void` / `accounting.voided_entries.read` are registered in `contracts/postgres-business-rules-v1.json` (reference domains, versioned seed). Guards treat only the structural terminal states (`POSTED`, `VOIDED`, `DRAFT`) as literals; every other state value stays reference data. D-014 keeps Voided Entries readable by normal module access: visibility policy is future application RBAC, never a database role rule, and delete authority remains a separate mechanism (module read cannot execute the void).

Limits: no application route, page, confirmation flow or RBAC setting is delivered here (AUTH-006 and PIVOT-013 gate application acceptance; a UI contract owns the Delete/Voided pages). The database primitive is the contract; a denied attempt's durable security log is written by the application because PostgreSQL has no autonomous transaction.

## Tenant change audit (PIVOT-006)

PIVOT-006 adds payload `041-audit.sql` and registers it in `40-triggers.sql` alongside 040/042. The dispatcher attaches the audit writer to the reviewed tenant business tables and attaches native-insert and append/TRUNCATE guards to the audit streams. It never edits the applied 040/042 payload bytes and retains every prior binding. Applying 041 is required for PIVOT-006 audit coverage; `40-triggers.sql` attaches and validates it when present. A 040/042-only installation remains runnable for PIVOT-005 but explicitly does not claim PIVOT-006 audit coverage.

- `tenant_data.audit_event` receives one append-only row per audited business INSERT/UPDATE/DELETE, in the same transaction as the mutation. The row carries the verified tenant and acting actor id, the action (`INSERT`/`UPDATE`/`DELETE`), target table and catalog-derived primary-key target identity, a versioned before/after snapshot, the transaction id, validated `origin_type`/`origin_user_id`/`origin_model`/`origin_model_version` and the event time.
- The acting actor is resolved only from the transaction-local AUTH-006 context and the tenant-local `members` projection; a client-supplied actor, `created_by` or `updated_by` value can never become the audit actor. Missing/foreign context or an unmapped principal raises `AUDIT_CONTEXT_REQUIRED` / `AUDIT_ACTOR_UNVERIFIED` and rolls back the business mutation.
- The dedicated `saven_audit_definer` NOLOGIN owner runs the `SECURITY DEFINER` audit writer and native-audit actor-binding guard with exact fixed `search_path`s. Its authority is validated against an exact allow-list: enumerated `members` and `reference_values` mapping reads, enumerated `audit_event` column INSERT, `audit_event_id_seq` USAGE and the narrow `current_tenant_id` / `current_user_id` / `session_admitted` helper calls. It has no runtime `EXECUTE` grant, business-table write, table/schema CREATE, broad auth/operator read or superuser/BYPASSRLS. A polluted pre-existing role is refused and left untouched.
- Native `tenant_data.audit` inserts are bound to the admitted canonical tenant/actor (`AUDIT_ACTOR_MISMATCH` on a spoofed/invented actor). Historical native ids, bytes, timestamps and counts are never rewritten, mirrored or back-filled; command-linked and void-definer inserts remain atomic with their transaction.
- Before/after snapshots use a versioned serialization contract (`serializationVersion` 1) bound to an exact per-table schema fingerprint over ordered column names and **catalog type identity** (resolved base type OID plus effective typmod). Type identity is resolved through `pg_catalog` type kind/base identity; domains are followed recursively to their base type and typmod. There is no type-name string comparison in 041. The reviewed inventory covers every registered table, including `numeric(20,4)` (`approval_policy` thresholds/self-approval) and `numeric(9,6)` (`tax_profile.rate`); parameterized numerics retain their exact JSON numeric value with no float cast or rounding. Structured scalar columns and reviewed business text are retained; JSONB and unreviewed text are replaced with a redacted digest marker and listed in `redactedColumns`. A custom domain over text follows the text policy (redacted where the column is not reviewed for raw retention); a custom domain over numeric follows the exact numeric policy. A new, renamed or retyped column raises `AUDIT_SERIALIZATION_SCHEMA_CHANGED`; a genuinely unknown base type raises `AUDIT_SERIALIZATION_UNSUPPORTED`; both roll the mutation back. A new text column whose name is allow-listed on another table therefore cannot inherit raw retention.
- **Unrepresentable-type decision (explicit): fail closed.** There is no redact-and-warn fallback for an unreviewed base type. The serializer and activation cannot represent it safely, so the business mutation is refused, and a new column/type requires a reviewed serialization version/inventory update before it can be audited. This decision is part of the version 1 contract.
- **Pipeline alarm:** activation enumerates every table actually attached to the audit writer and refuses if its schema fingerprint differs from the reviewed inventory or any column base type (domains resolved) is not in the exact representable-type OID allow-list. The focused test also enumerates every column type actually present across the registered inventory and fails if the reviewed type set changes. Original financial/source bytes remain intact; this is a redaction boundary in the sidecar, not a claim that arbitrary free text can be made secret-free.
- Provenance is never manufactured as human. For document/proposal tables with explicit origin columns, `origin_type` must be an active canonical `reference_values` value; AI requires a model and a tenant-member proposer, human cannot name a model and falls back only to the verified actor when `origin_user_id` is absent, integration requires an identity or model, and model/version are retained. Generic tables with no explicit origin record genuinely unavailable provenance as `system` with `detail_jsonb.provenance='unavailable'`; the verified acting principal remains `actor_id`. A client GUC cannot manufacture document origin.
- `tenant_data.audit` (native command-linked audit) is preserved exactly. The audit writer defensively skips `audit`/`audit_event`, and the dispatcher never attaches the change writer to audit storage, so there is no recursive audit loop.
- Audit storage is append-only at the database boundary: row `UPDATE`/`DELETE` on `audit` or `audit_event` raises `AUDIT_IMMUTABLE`; `TRUNCATE` raises `AUDIT_TRUNCATE_DENIED`. The runtime already lacks those privileges and the guards also protect against accidental owner/administrative mutation.
- Activation boundary: 041 is function-only and is **not audit-active** until 40-triggers completes. The dispatcher attaches and validates every audit and 040/042 trigger in one transaction; any failure rolls the whole set back and leaves no partial audit-active claim. Operators must quiesce business writes from 041 application through successful 40-triggers activation and then verify the attached guard/version set. There is no silent unguarded interval claimed as covered.
- Bootstrap/import changes must complete before 041/40 activation, or use a future separately reviewed audited maintenance path. Context-less administrative DML after activation fails closed rather than fabricating a historical actor.
- This payload records committed business mutations. A failed or denied access attempt cannot rely on the same rolled-back transaction for durable evidence; denial/security-event durability remains the separately owned application/kernel workflow (PIVOT-013), not a claim of this change-audit payload.

Audited business tables are an explicit reviewed list in `40-triggers.sql` (accounts, journals/lines, trade/stock, documents, roles/members/assignments, periods, policies, configuration and related Purpose B/C tables). Audit storage itself (`audit`, `audit_event`), command delivery infrastructure (`command_inbox`, `outbox`), imported provenance (`source_store_migrations`) and PIVOT-005's own `entry_voids`/`void_denials` are intentionally not re-audited by the generic writer; their native audit/denial semantics remain authoritative. A new audited table requires an additive registration in the dispatcher plus serializer/provenance review, not a silent catalog sweep. Document-origin audit also requires the canonical active `origin_type` reference rows; missing rows fail closed.


## Audited operator reads (PIVOT-007)

`50-functions.sql` adds the single cross-tenant read boundary. It is not a generic SQL endpoint and exposes no table name: the reviewed resource allow-list is `business`, `company_profiles`, `accounts`, `journals` and `journal_lines`, each with an explicit column projection. `business` and `accounts` are **tenant-wide** projections and reject a company selector; `company_profiles`, `journals` and `journal_lines` are company-scoped and are filtered by the grant's `companies` list and by an explicit `p_company` selector.

**Bearer proof and configured identity.** The caller supplies a transaction-local `app.operator_session_id` plus `p_session_proof`, the lowercase SHA-256 hex digest of the raw operator session token. The digest is compared with `auth.sessions.token_hash`; a caller-nominated session UUID alone is not proof and no raw bearer value is stored in arguments, audit metadata or results. The function then resolves `operator.access_session_binding` → `operator.access_identity` → `auth.users` → `auth.roles` and revalidates: `generation-v1` binding scheme; binding/mapping generation, role and assurance equality; active mapping/principal; operator role with `requires_mfa`; effective windows; `realm = 'operator'`; non-revoked, unexpired idle/absolute session; `auth.users.credential_version = auth.sessions.credential_version`; unexpired assertion; and the configured issuer, audience, exact `required_assurance` and maximum source age/skew from the versioned `operator.access_read_policy` table. A missing, inactive or non-effective policy fails closed with `OPERATOR_POLICY_REQUIRED`. The policy schema pins the mandatory `access_mfa` assurance with a CHECK constraint and the function re-checks it, so a coherent weaker-label rewrite of the policy, mapping and binding still fails closed.

**Trusted time and gate protocol.** The function validates the installed AUTH-006/AUTH-007 writer protocol before trusting it: the reviewed exclusive `auth.lock_authority_gate()` body and owner, every gated `tenant_membership`/`roles`/`access_identity` trigger enabled in origin mode and bound to the exact function/event, plus the PIVOT-007 consent gate. Omitted, disabled, replica-only or misbound protections raise `OPERATOR_AUTHORITY_PROTOCOL_INVALID` and no read occurs. The function takes the AUTH-006 authority gate **shared**, locks principal then session `FOR SHARE`, sets the tenant context, takes the consent gate shared, takes the read-policy writer gate shared, and only then samples `clock_timestamp()`. Every blocking acquisition precedes the final identity/session/source/grant checks, and the selected `operator.access_read_policy` row is selected/revalidated with that final time after the last gate, so a policy, session, assertion or grant that expires while waiting cannot pass on an earlier timestamp. The consent and policy gates are held through the read/audit commit; policy writes are serialized by the policy gate. Trigger validation also requires unconditional statement triggers (`tgqual IS NULL`), no arguments/columns/deferral, origin firing mode, and the exact invoker/plpgsql/trigger/`search_path=pg_catalog` function profile; a `WHEN (false)` or re-profiled gate is refused.

**Customer consent lifecycle.** `tenant_data.support_grants` is the consent record, keyed by exact Access subject. A read takes the shared side of a second advisory gate (`saven.operator.consent_gate`); `BEFORE STATEMENT` triggers on `tenant_data.support_grants` and `tenant_data.members` take the exclusive side for INSERT/UPDATE/DELETE. Customer revocation, scope/company narrowing and `members.active` changes therefore serialize against an in-flight read: a writer starting first blocks the read and a committed revocation is observed; a read starting first blocks the writer until its transaction ends. The read revalidates the grant window, exact JSON scope and the authoring member's active status after acquiring the gate. Consent writers should update the grant before the member row in one transaction; both orders serialize but a consistent order avoids avoidable deadlocks.

**Grant shape.** `scope_jsonb` is versioned JSON, shape version `1`:

```json
{"version": 1, "resources": ["journals", "journal_lines"], "companies": ["alpha"]}
```

`version` must be a JSON number `1`; `resources` is a required array of non-empty strings; `companies` is an optional array of non-empty strings (absent means every company in the tenant). All array elements are type-checked as strings before use; there is no `->>` coercion, unknown keys fail closed, and a company selector outside the grant is denied. `actions_jsonb` must be an array of non-empty strings and contain the exact requested action key. The authoring `granted_by_user_id` must still map to an active `tenant_data.members` row. A reason string is required for accountability but never substitutes for a grant.

**Atomic audit and honest denial evidence.** A successful read inserts one `operator.operator_audit` row in the same transaction (local operator actor, `OPERATOR_READ`, tenant, reason, request id, Access subject/role/mapping generation/session/issuer/audience/assertion time, grant id, counts). If the insert fails the read fails; SQL cannot commit inside the caller's transaction, so the commit barrier belongs to the mediated adapter below. A refused read raises `OPERATOR_CONTEXT_REQUIRED`, `OPERATOR_ACCESS_DENIED`, `OPERATOR_ACCESS_EXPIRED`, `OPERATOR_POLICY_REQUIRED`, `OPERATOR_AUTHORITY_PROTOCOL_INVALID`, `OPERATOR_GRANT_REQUIRED`, `OPERATOR_RESOURCE_UNSUPPORTED` or `OPERATOR_ARGUMENT_INVALID` and writes nothing. The application must call `operator.log_operator_read_denial(...)` in a **fresh transaction**. That function verifies the same durable identity (digest, liveness, credential epoch, mapping continuity, role/assurance, configured policy) before attributing an actor; if any check fails it records `actor_id = 'unverified'`, `attribution = 'unverified'` and only labelled `claimedSubject`/`claimedSessionId` metadata, so an old or reassigned binding is never attributed to a current principal.

**Least privilege and authority validation.** All three functions are `SECURITY DEFINER`, owned by `saven_operator_definer`, with `search_path = pg_catalog, operator, tenant_data`, static schema-qualified SQL and no dynamic SQL. The two runtime functions are executable only by `saven_operator_read`; the internal protocol validator has no runtime grant. The payload revokes the broad bootstrap operator-table/sequence grants from the definer and re-grants only: enumerated column reads on the identity/policy/grant/projection columns, INSERT on `operator.operator_audit`, USAGE on `operator_audit_id_seq`, EXECUTE on `tenant_data.current_tenant_id()`, and two lock-only UPDATE columns (`auth.users.status`, `auth.sessions.revoked_at`) required by `FOR SHARE`. `operator.assert_operator_definer_authority` enumerates the complete surface before and after installation — role flags/settings, direct and transitive memberships, owned objects, schema/database/default ACLs, every table/column/sequence/function grant, PUBLIC reachability and the known bootstrap grants — and refuses any excess without stripping unrelated rights. The runtime protocol validator also rechecks membership/ownership/schema-CREATE drift on every read. The definer owns no table, cannot create in any schema, is not a member of any runtime role and has no `BYPASSRLS`; the read scopes `app.current_tenant_id` itself, restores the caller's value, and FORCE RLS still applies.

**Required deployment setting.** After installation the deployment must seed the versioned read policy; until then every read fails closed:

```sql
INSERT INTO operator.access_read_policy(
  policy_key, version, issuer, audience, required_assurance,
  max_source_age_seconds, max_clock_skew_seconds, is_active, effective_from, created_by)
VALUES ('operator_read', 1, '<verified issuer>', '<verified audience>', 'access_mfa',
        300, 60, true, now(), 'deployment');
```

A policy change is a new `version` row with an effective date; do not mutate a used row. No runtime role has access to this table.

**Publishing adapter (implemented).** `src/operator/support-read.mjs` is the only authorized path that may return rows. It verifies the genuine bearer through accepted AUTH-007 `inspectSession` as a completed preflight, then independently calls this SQL boundary on one owned operator-read client/transaction with the bearer-derived digest and transaction-local session context. It compares the actual AUTH-007 captured policy descriptor (issuer/audience/fixed `access_mfa`/source-age/skew) with the configured expected policy and with the SQL policy fingerprint, and compares the verified subject/role; any drift discards rows. Only then does it `COMMIT` and return rows. Missing/short/oversize bearer refusals are recorded as independent unverified denial evidence before the caller sees the refusal. On refusal it rolls back, destroys that exact client, releases it, and writes denial evidence in a separate denial transaction; failure to commit denial evidence is exposed as `denialLoggingFailed` without replacing the original error. It keeps the separate restricted auth and operator-read logins, never assumes auth-service EXECUTE, never logs raw bearer values or digests, and supports a size-one operator pool. See `src/operator/README.md`.

No HTTP route, UI, session-cookie handling, OpenAPI entry point or auth-service EXECUTE grant is added.

## RLS and privilege coverage gate (PIVOT-008)

`99-ci-rls-coverage.sql` is the target database release gate. It is intentionally a single read-only query; it is not applied as a migration, never repairs a violation and never grants anything. `scripts/verify-pg-rls.mjs` runs it and turns **any** returned row into a nonzero exit, so a coverage regression cannot pass as a zero-row query with a successful process status.

The gate fails on:

- **a missing installed-surface obligation**: the reviewed manifest requires all three schemas, the ten bootstrap/definer role classes, the 49 tenant tables plus the 11 auth and 15 operator tables, the two tenant views, the reviewed sequences, the protocol/definer function signatures, the 18 AUTH-006/AUTH-007 consent-policy writer triggers plus the 040/041/042 payload guards, and the versioned `operator.access_read_policy` columns and mandatory `access_mfa` constraint. An empty schema set, one missing table, one missing role or one missing function fails with its own diagnostic; a minimum count cannot stand in for the accepted release;
- **an incomplete effective policy contract per command and principal**: for `SELECT`, `INSERT`, `UPDATE` and `DELETE`, a permissive isolation policy and a restrictive scope policy must both cover the command with the required `USING`/`WITH CHECK`, and a restrictive customer-admission policy must cover it with `session_admitted`. Membership must keep its principal-bound `SELECT` preselection per role with restrictive partners and must reject permissive write policies;
- **transitive unsafe paths**: views, materialized views and inheritance children are followed across schemas, cycle-safely, to the published endpoint. A nested view over an inner view, a materialized-view wrapper, or a multi-level child with a column-only grant is evaluated at the endpoint; an intermediate object without a direct grant is not assumed safe;
- **effective authority drift**: table, column, sequence, function and role-switch authority are compared with the accepted per-runtime profile, including current-user login roles and direct/transitive membership. Customer-to-auth/operator, auth-service-to-tenant, operator-to-tenant and operator-to-auth access, column-only grants, `NULL` function ACLs (PostgreSQL default `PUBLIC EXECUTE`), the PIVOT-007 `EXECUTE` allow-list, direct login grants, cross-class role switching and non-registered privileged principals are all violations;
- **definer or protocol drift**: a `SECURITY DEFINER` function without a fixed `pg_catalog`-first `search_path`, owned by a `SUPERUSER`, `BYPASSRLS` principal or login role, executable by `PUBLIC`, disabling `row_security`, or assumable by a runtime role; a definer owner with a relation or `EXECUTE` grant outside its reviewed manifest; and any required writer/consent/policy trigger or helper that is missing, disabled, replica-only, conditional, misbound or reprofiled;
- `PUBLIC` holding a relation, column, sequence or `SECURITY DEFINER` execute privilege, and runtime `TRUNCATE`/`REFERENCES`/`TRIGGER` on tenant data.

Commands:

```text
node scripts/check.mjs              # parser/native build check; no PostgreSQL needed
node scripts/check.mjs --postgres   # same check plus the coverage gate
```

`--postgres` requires the same disposable/test PostgreSQL opt-in as the fixture: `SAVEN_PIVOT_TEST_CLUSTER=1` plus a loopback administrative connection (`PGHOST`, `PGPORT`, `PGUSER`, optional `PGPASSWORD`/`PGSSLMODE`, `PGADMIN_DATABASE`). With no `--database` argument it creates a private database, applies the full accepted stack in the order above, runs the coverage query and the accepted read-only protocol validators (`operator.assert_read_authority_protocol()` and `operator.assert_operator_definer_authority('post', false)`), then drops the database. `scripts/verify-pg-rls.mjs --database <name>` runs the same checks against an already provisioned database (used by the focused test).

The runner exits through one cleanup path, never inside a connection helper. It drops a temporary database only after its own `CREATE DATABASE` succeeded, refuses to reuse or drop a pre-existing name, reports a failed/uncertain creation without dropping it, and prints `RESIDUE` with the retained target plus every primary/cleanup error. Test-only seams (`--temporary-name`, `--inject-failure-after-create`, `--inject-drop-failure`) make collision and cleanup failures deterministic; they do not bypass authentication or the disposable-cluster opt-in. If the cluster, credentials or opt-in are absent, the gate exits nonzero with an actionable message; it never reports a skip as success. `.github/workflows/postgres-pivot.yml` runs this gate and `tests/pivot-008-coverage.test.mjs` on every push/PR to `testing-1`/`main` against a disposable `postgres:18` service.

**Extension points and limits.** The role registry is resolved from the reviewed bootstrap prefix (deployment `saven_`, fixture `saven_pivot_<suffix>_` derived from the schema owner), and each class is an explicit registration. A new runtime class is added to the bootstrap and this manifest together; an unrelated role cannot satisfy a class by a loose name suffix and is flagged as a non-registered privileged principal if it gains covered authority. A new release-required relation, function, trigger or sequence is added to the reviewed manifest; new tenant tables are covered automatically by the catalog checks but must still ship their policies and grants in the same migration. The catalog contract is supplemented by real restricted-login behavioral tests: own-tenant positive controls, foreign/no-context refusals, retained rows after denied mutations, membership preselection, and a nonliteral always-true predicate that the catalog cannot semantically disprove. The gate does not prove application-level approval, company/branch or amount authority, and it is not a runtime security monitor. A catalog bypass through object ownership remains an operational trust boundary (see the limits above).

**Operator read extension points and limits.** A new readable resource is a reviewed static allow-list addition plus its column grant; it is a widened privileged capability, not a reference row. A new scope key or JSON shape requires `version: 2`. Action keys and company labels are customer-grant data; statuses use reference data; no new `CHECK` list or hardcoded growing domain is introduced. No bulk export, cross-tenant aggregate, raw SQL, table-name parameter, write or impersonation mode exists. Operator read visibility is subject to the grant scope but is **not** a substitute for future application RBAC (D-014). Denial durability depends on the adapter's independent transaction.

The `operator` schema is cross-tenant by design and has no tenant RLS. Customer and auth roles have no schema, table, sequence or function privileges on it.
- `saven_operator_read` has `SELECT` on the current operator tables. New operator tables require an explicit grant.
- `saven_operator_admin` can insert/update operational records. It has `SELECT, INSERT` only on `operator.entitlement`; it cannot mutate or truncate issued entitlement rows, and it cannot update or delete the append-only audit/provenance ledgers.
- Append-only tables and issued entitlements reject every `UPDATE`, `DELETE` and `TRUNCATE` with `OPERATOR_RECORD_IMMUTABLE`, including for the migration owner. `TRUNCATE` is refused by statement-level triggers because it does not fire row `DELETE` triggers.
- The actual `00-roles.sql` bootstrap never runs `ALTER ROLE`. It validates all seven target definitions and refuses incompatible pre-existing roles before creating anything; compatible reruns are a no-op and preserve existing memberships and grants. Roles outside the seven target names are untouched.
- Runtime logins are separate from the offline migration login and have no direct or transitive membership in `saven_migrator`, `saven_operator_definer` or `saven_auth_definer`. Tests assert this, assert actual schema/table/index/sequence/function ownership, and exercise denied `SET ROLE`, `ALTER` and `DROP` through runtime connections.
- Migration and source-provenance ledgers are separate. Native SQLite migration checksums are not asserted to be PostgreSQL SQL checksums.
- Reference values are seeded/declared, not enforced by foreign keys or triggers. Effective-dated policy, JSON-schema validation and financial entitlement activation are deferred and must not be described as implemented.
- Object ownership can alter or drop these guards. Ownership is an operational trust boundary, not tamper-proof audit storage.
- `tenant_data` runtime access is granted directly only to `saven_customer_app`, together with forced RLS and the isolation/admission policies in `30-rls-policies.sql`. The dedicated NOLOGIN admission, void and audit definers hold only their enumerated helper/function and column grants; PUBLIC, `saven_auth_service`, `saven_auth_definer` and every operator role hold no tenant privilege. An absent, empty or malformed tenant/user context denies rather than falls back, `FORCE` RLS applies to the table owner, and no role has `BYPASSRLS`. RLS is isolation only and is not a substitute for company/branch/resource/approval enforcement.
- A runtime request must set both context GUCs transaction-locally from a verified session. Code that queries `tenant_data` without the AUTH-006 context sees zero rows; that is the intended fail-closed behavior, not a bug to work around with a table grant.
- No credentials, DSNs, superuser grants or BYPASSRLS grants are present.
- `auth` is default-deny for customer and operator roles. The auth service writes identity/session state only; it is not a tenant-data reader, and AUTH-002/006 must prove server-verified selection before any business request.
- `auth.tenant_membership` is forced and isolated with two principal-bound policies (preselection for the auth service, single-pair admission lookup for the dedicated owner). Membership writes have no policy and therefore fail closed until the contract that implements invitation/acceptance adds its own reviewed policy. `auth.users` and `auth.sessions` are global principal/service records and keep a separate authority boundary rather than blanket tenant policies.
- The admission helper is owned by the dedicated `saven_tenant_admission_definer`, not by the migrator. It binds its arguments to the verified transaction context, so it cannot be used as an arbitrary-principal membership oracle, and no runtime role is a member of it. Its full authority is validated against an exact allow-list, and membership access is protected by permissive+restrictive pairs so a future permissive policy cannot widen it.
- Sessions, verification challenges, recovery codes and OAuth state are digest-only; TOTP seeds, provider tokens and PKCE verifiers are ciphertext with a versioned key. The absolute session ceiling is immutable by trigger.

## Extension points

- Add operator domains as `operator.reference_value` rows with `is_active` and effective dates; do not add a growing CHECK list. The bootstrap seeds and declares these domains but does not enforce FK/reference lookups, effective-dated policy or JSON schemas. Application validation and activation are deferred and explicitly non-authoritative here.
- Store versioned operator configuration in `value_jsonb`/`claims_jsonb` with a documented schema version. `feature_flag.value_schema_version` and `entitlement.claims_schema_version` bind the intended shape, but JSON-schema validation is deferred.
- Add future operator tables with explicit grants to the read/admin/definer roles and an explicit append-only/truncate decision where mutation is prohibited.
- PIVOT-003 adds the tenant business/rule table skeleton; PIVOT-004 adds forced RLS, the three-policy isolation/admission model, least-privilege runtime grants and the constrained auth principal projection; PIVOT-005/006 add posted-source immutability and business audit; PIVOT-007 adds the audited, customer-granted operator read boundary owned by `saven_operator_definer`; PIVOT-008 adds RLS coverage; AUTH-001..010 add the canonical auth schema (AUTH-002/006 still own forced auth-side RLS and verified context).
- Adding a `tenant_data` table requires its policies and grants in the same additive migration: `ENABLE` + `FORCE` RLS, a permissive tenant-isolation policy, a restrictive tenant-scope policy, a restrictive `saven_customer_app` admission policy, an explicit grant row in the matrix above, and coverage in the PIVOT-008 query. A table without all of them must not be merged. The same applies to a partitioned parent/child: coverage checks use `relkind IN ('r', 'p')`, so a partition cannot inherit trust it was never granted.
- A new tenant-scoped `auth` table needs its own narrow, principal-bound policy in its own contract; do not copy the membership policies onto global principal or session tables, and do not add a blanket bootstrap policy. Any role granted membership (or other principal-scoped) access needs both a permissive policy and a restrictive partner with the same predicate, so a later permissive policy cannot widen it.
- A change to the helper's owner or privileges requires re-running the authority validator: `032-rls-hardening.sql` is the template for an exact allow-list that refuses rather than repairs.
- Adding a company-scoped tenant column requires a parent link to `tenant_data.company_profiles (tenant_id, id)` (added `NOT VALID`, then validated) plus a lookup index. Country/company data inside JSON payload bytes stays application-validated and belongs in the inventory table above when added.
- Changing the authenticator, session model or tenant-selection contract means revisiting `session_admitted()` in the same contract: the admission predicate is canonical membership plus an active tenant principal, and it must not start reading documents, credentials or sessions to answer.
- Tenant reference data: add domains and values as `tenant_data.reference_values` rows with `is_active`/effective dates and a `value_schema_version`; keep the seed list in `contracts/postgres-business-rules-v1.json` current. Do not add a growing `CHECK` list, and never let a reference row install posting/authorization logic — that requires a registered typed handler plus tests.
- Tenant policy: add a new `version` row in `business_rule`/`approval_policy`/`posting_constraint`/`tax_profile` instead of mutating a used row, and validate `*_jsonb` against the versioned JSON schema named in `contracts/postgres-business-rules-v1.json`. Nested configured values such as `posting_constraint.rule_jsonb.severity` resolve through their named reference domain; they are never inlined as JSON-schema enums.
- Stock valuation: the native `quantity > 0 OR value = 0` relationship is enforced by a named validated constraint. Weakening or moving it requires an ADR and the posting/handler work, not a silent schema edit.
- Pending documents: extend `document_type`/`document_status`/`origin_type` reference values, not a table per document type. `document_registry` plus append-only `document_revisions` is the canonical path for both human and AI-origin pending work; accepted command bytes are never rewritten.
- Auth domains grow as `auth.reference_value` rows (assurance levels, statuses, purposes, algorithms, audit event types) and assurance classes as `auth.roles` rows; business/ERP roles and the protected ultimate-owner definition stay in `tenant_data`. Adding a connector, factor type or provider requires its own contract and adapter work.
- Recoverable auth secrets follow one convention: ciphertext, algorithm and key version together. A ciphertext without a non-null positive key version is invalid by constraint.
- Fully Private omits vendor operator tables and the vendor issuer; the same customer/auth/tenant contracts remain.

## Local gate fixture

`tests/helpers/pg-pivot-fixture.mjs` creates only `saven_pivot_<suffix>_*` cluster roles and a `saven_pivot_<suffix>` disposable database on a loopback PostgreSQL cluster. It requires `SAVEN_PIVOT_TEST_CLUSTER=1` as an explicit dedicated-cluster opt-in, rejects non-loopback hosts and SAVEN target-role credentials, and never falls back to an owner/shared cluster. A pre-flight check refuses before any mutation if any generated role or database already exists, so pre-existing cluster roles, memberships and grants remain untouched.
